# 发布物料

Status: ready-for-agent
Type: spec

## Problem Statement

主题的**对外发布**已经定了路线（见 ADR 0002：自托管分发，不进官方主题目录），但今天它**只能待在自己的站上**：

- **没有截图。** 别人装上去之后，在「外观 → 主题」里看到的是一张**空白卡片**——主题长什么样，得装上才知道。
- **没有能装的包。** 仓库里那份 `.distignore` 写得挺全，但**没有任何东西在读它**：这套环境没有 WP-CLI，就没有 `wp dist-archive`；仓库里也没有 `.gitattributes`。所谓「打包」是一条断的链路，今天根本出不了包。GitHub release 自带的那份源码 zip 顶不上——顶层目录名不对，还带着 `.git`、`tests/`、`docs/`。
- **没有人系统看过一遍它装到别人站上会不会出问题。** 主题一路长到现在，所有验证都发生在自己的站上、只验行为。

所以那句话到今天仍然成立：主题能用，但**还不能交给别人用**。

## Solution

补上三样，让**对外发布**落到实处：

**一张截图。** 主题包里带上真实渲染出来的首页截图，浅色形态，符合官方的尺寸与比例。使用者一眼看到的就是他装好之后的样子。

**一个可安装的包。** 打包从「一条断链」变成一件能重复做的事：排除清单只有一处，产出顶层目录名正确的 zip，并且**包的内容是可断言的**——将来改坏了会红，而不是发出去才发现。

**一次体检。** 跑一遍官方那个检查工具，把结论记下来。不是为了走那条路，是为了让**真 bug 不被「我们不走那条路」顺手放过**。

## User Stories

### 截图

1. 作为分发者，我希望主题包里带一张截图，这样使用者在「外观 → 主题」里看到的是主题的样子，而不是一张空白卡片。
2. 作为使用者，我希望不用装上去就能看出这主题长什么样，这样我能在装之前决定要不要用它。
3. 作为分发者，我希望截图是**首页**，因为一屏里就摆着这主题的招牌——圆点纹理的头部、暖白的底、纵向文章列表的节奏与缩略图。
4. 作为分发者，我希望截图是**浅色**形态，这样第一印象与该主题装好之后的默认一致。
5. 作为分发者，我希望截图是**真实渲染**出来的，不是拼的营销图，这样它既不撞官方「不得像广告」那条，也不会与实物不符。
6. 作为分发者，我希望截图是在**有真实内容**的页面上拍的，这样它展示的是有内容的站点，而不是一个空壳。
7. 作为分发者，我希望截图符合官方要求的尺寸与比例，这样将来真要走那条路时不必重做。
8. 作为使用者，我希望截图在深色模式下装出问题也不影响我看它——这个主题的深浅色是同一套设计的两面，一张图说清楚其中一面即可。

### 可安装的包

9. 作为使用者，我希望拿到一个能直接装的 zip，这样我不必自己从源码里挑文件。
10. 作为使用者，我希望 zip 解出来是**一个以主题 slug 命名的目录**，这样 WordPress 认得出它是一支主题。
11. 作为使用者，我希望包里没有 `.git`、`tests/`、`docs/`、`.scratch/` 这些与主题无关的东西，这样我拿到的是主题本身，不是我们验证它的基建。
12. 作为使用者，我希望包里带着许可文件，这样我一眼知道它是什么授权。
13. 作为使用者，我希望包里带着截图，这样我解压之前就知道它的样子。
14. 作为分发者，我希望**排除清单只有一处**，这样我不会把两份清单改漂。
15. 作为分发者，我希望打包**不需要 WP-CLI**，这样在这台机器上也能出包。
16. 作为分发者，我希望包的构成是**可断言的**——哪些文件必须在、哪些必须不在——这样将来漏掉一个、或多带一个，会有一处变红。
17. 作为分发者，我希望这件事**明年还能重复做**，而不是只有第一次做对。

### 体检

18. 作为分发者，我希望跑一遍官方那个检查工具，这样装到别人站上不至于出现明显的规范问题。
19. 作为分发者，我希望**检查的结论有记录**，这样下次改动时我知道当时的基线在哪。
20. 作为分发者，我希望即便不走官方目录，也**按同一把尺子看一眼**——那些「Required」项里有一部分本来就是真 bug，不该因为「我们不走那条路」而被顺手放过。
21. 作为分发者，我希望这次**不做功能开发**——除了修检查暴露出来的真缺陷，主题行为不变——这样发布准备不会变成一次功能迭代。
22. 作为分发者，我希望 `style.css` 的头部字段齐全，这样主题在后台被正确识别——版本、兼容范围、翻译域都在。
23. 作为使用者，我希望主题声明它测试过的 WordPress 版本，这样我能判断它跟不跟得上我自己的站。
24. 作为使用者，我希望主题声明它的翻译域，这样它被翻译时字符串能被正确归组。
25. 作为分发者，我希望这次检查**不写进每次验收**——它依赖一个第三方插件装在**共享**的本地环境里，写进验收脚本会让脚本变成「谁没装插件谁红」。
26. 作为分发者，我希望检查的环境依赖是**已知且已装好的**，而不是每次重新摸索。
27. 作为分发者，我希望检查暴露出来的**真缺陷当场修掉**，而不是记一笔留到下次——留到下次就是永远不修。
28. 作为访客，我希望文章用分页（`<!--nextpage-->`）时能看到翻页链接，这样我够得着第二页。
29. 作为站点所有者，我希望那一页的 `<title>` 由主题统一的机制产出，而不是在那一页硬写一个，这样标题规则只有一处。

### 边界

30. 作为分发者，我希望这次**不动一言与头像镜像的默认值**（见 ADR 0002），这样发布准备不会顺手推翻一个已经拍过的取舍。
31. 作为分发者，我希望**不写 `readme.txt`**——自托管分发下它不是必需的。
32. 作为分发者，我希望主题保持 **100% GPL 兼容**，这样自托管分发是干净的。
33. 作为使用者，我希望手里的主题包**不包含任何测试环境的痕迹**，这样它和「自己站上跑的那个」是同一个东西。

## Implementation Decisions

### 通用约束

- 目标形态是**对外发布**的**自托管**路线（ADR 0002）：出包、交给人；**不进官方主题目录**。
- 不引入构建步骤，不引入前端框架。新增脚本只能是能直接跑的原生脚本，与现有的几个同级。
- 本次**不做功能开发**。除「体检」那一节要修的两处缺陷之外，主题的行为不变。

### 截图

- 顶层 `screenshot.png`，**1200×900（4:3）**。官方的硬线是「不大于 1200×900」与「宽高比 4:3」，取上限。
- 内容是**首页 · 浅色**。浅色是主题的默认形态；深色很上镜，但它是变体，拿变体当门面会让第一印象与装上之后的默认对不上。
- 由**无头浏览器**在设好视口之后截图产出，**不是** `msedge --screenshot --window-size` 那类老办法——那个按更宽的默认布局渲染再裁，看着像横向溢出，本仓库已经踩过一次。
- 拍摄前页面必须**有真实内容**：几篇带缩略图的文章、若干分类。不需要评论。
- 给既有的浏览器观察点**加一个截图方法**。这是给既有观察点补一只眼睛，**不是新建 seam**；改动只增不改。

### 打包

- 写一个 Node 脚本产出一个可安装的 zip，**读 `.distignore` 作为排除清单的唯一事实来源**。
- **不新增 `.gitattributes`。** 两份排除清单漂掉之后不会有任何测试变红，只会有一天发给别人的包里多了东西。
- **不依赖 WP-CLI**。本机已经装了，但 `dist-archive` **不在标准 phar 里**——它是单独的 `wp-cli/dist-archive-command`，装上落在用户全局目录（仓库之外）。那意味着每台要出包的机器两次额外安装，且都在仓库管不着的地方；而 Node 是任何能跑验收脚本的人本来就有的。
  - 代价要认：`.distignore` 的格式允许通配与取反，自写的读取器未必都覆盖。**读取器遇到看不懂的行必须报错停下**，而不是默默跳过——默默跳过就是「包错了但没人知道」。
  - 兜底是有的：包的内容由验收脚本断言（见 Testing Decisions），打错了会红。
- zip 解出来必须是**一个以主题 slug 命名的顶层目录**。这不是形式——目录名不对，Theme Check 会直接报出来。
- `.distignore` 的现状保持不变：`README.md` **留在包里**（主题带一份 readme 是正常的），`AGENTS.md`、`CONTEXT.md`、`DESIGN.md` 出包。

### 体检

- 跑一遍 **Theme Check**，结论（Required / Warning / Recommended 的计数与条目）记进本工单。
- 走官方的 `wp theme-check run <主题>`。WP-CLI 与 Theme Check 插件都已装在本机开发环境里，命令已注册，不需要再找别的办法。
- **必须对「打包后的样子」跑，不是对工作区跑。** 工作区里住着 `tests/`、`docs/`、`.scratch/`，它们被 `.distignore` 排除在包外，却会被 Theme Check 逐文件扫到。实测：工作区比产物**多出 9 条 REQUIRED 与 10 条 WARNING 的假阳性**（fixture 脚本里的 `fwrite`，以及中文提示文案里的小写 `wordpress`）。照工作区的结论去改，就是在追一批根本不会发出去的文件。
- Theme Check **不进验收脚本**：它依赖一个第三方插件装在共享的本地环境里，写进验收会让脚本变成「环境不对就红」。它是发布前跑一次的门，不是每次验收的断言。
- `style.css` 头部补齐两处：**`Author`**（当前值由站主定）、**`Tested up to`**（写本地实跑的那一版，当前是 `7.1`）。已有那十项不动。
- 按官方那套尺子看一遍，但**只修真 bug**。判断标准写死：**它是不是一个使用者会撞上的功能缺陷或呈现缺陷**。是就修；只是「少一行声明」「少一个 class 名」而不产生可见后果的，记进本工单的结论里，不修。
- 这一轮**唯一动到主题代码**的两处，就是标准筛出来的这两条：
  - **补 `wp_link_pages()`。** 文章模板里没有它，用分页标记的文章读者够不着后续页。这是官方的 REQUIRED 项，也确实是缺陷。
  - **拆掉确认页硬编码的 `<title>`。** 主题已经声明了 `title-tag` 支持，那一页却绕过去自己写了一个。
- 结论里**够格但不修**的那类要写清楚：编辑器样式与区块支持（`add_editor_style`、`responsive-embeds`、`align-wide`、`wp-block-styles`）、对齐与图注的 CSS 类（`.alignleft`/`.alignright`/`.aligncenter`、`.wp-caption`、`.gallery-caption`）、`Theme URI`/`Author URI`、`style.css` 的 `minimal` 与 `light`/`dark` 标签、block patterns、版权声明。前两组有可见后果，但属于设计工作——另立一件，见 Further Notes。

### 明确不做的

- **不写 `readme.txt`**（自托管下非必需，见 ADR 0002）。
- **不按官方 Required 清单全量过审**。
- **不动一言与头像镜像的默认值**（ADR 0002）。
- **不提交官方目录**。

## Testing Decisions

### 什么算一个好测试

只断言**产物与外部可观察的行为**，不断言实现细节。

具体说：断言「包解出来顶层目录名是主题 slug」，而不是「打包脚本调用了某个函数」；断言「截图是 1200×900 的 PNG」，而不是「脚本里写了一个尺寸常量」。实现方式换了、测试不该红；产物变了、测试必须红。

### Seam

**不新增 seam。** 这一件验的是**产物**，不是「请求进去、HTML 出来」那类行为——仓库既有的两个观察点正好够：

1. **无头浏览器**——截图由它产出，截图的成色也由它量。
2. **文件阅读**——现有的 CSS 解析辅助已经把 `style.css` 读成文本（并统一了行尾），头部字段那条断言直接用它，不重写解析。

Theme Check 走官方的 WP-CLI 命令，**但它不进验收脚本**（理由见上）。它是发布前跑一次的门，不是一次断言。

### 要测的模块

- **截图**：文件在顶层、是 PNG、尺寸 1200×900、宽高比 4:3；并且它**确实是一张渲染出来的页面**——不是纯色、不是空白。
- **`style.css` 头部**：官方列的字段齐全，含这次新增的两项。
- **包**：解出来顶层目录名等于主题 slug；必须**在**的文件（样式表、首页模板、评论模板、截图、许可）；必须**不在**的东西（`tests/`、`.scratch/`、`docs/`、版本控制目录、`.distignore`、以及三份协作文档）。

### 明确不测什么

- **Theme Check 的结论**——依赖第三方插件，不进验收脚本，结论记进工单。
- **官方 Required 清单里的那些项**（前缀、经典主题钩子、必备 CSS 类、转义审计）——这一轮不按那把尺子过，也就没什么可断言的。
- **WordPress 自身的安装行为**——那是平台的事。

## Out of Scope

- **`readme.txt`**。自托管分发下它不是必需的；将来要走官方目录再补。
- **官方 Required 清单的全量过审**：函数与句柄前缀、经典主题必备钩子、必备 CSS 类、全量转义审计。
- **前台呈现与编辑器对齐**：编辑器样式、区块支持、对齐与图注的 CSS 类。Theme Check 把它们报成 RECOMMENDED，其中几条确实有可见后果，但那是设计工作，另立一件。
- **一言与头像镜像改成默认关闭 + 披露**。那会推翻 ADR 0002，是一件该单独拍板的事。
- **提交官方主题目录。**
- **主题的任何功能行为改动。**
- **深色形态的截图**，以及任何多张截图 / 拼贴图。
- **发布后的维护流程**（版本号策略、更新分发、changelog 维护）。

## Further Notes

- **ADR 0002 约束着这一块。** 任何「顺手把一言改成 opt-in 以符合官方要求」的想法，都要先推翻它，而不是绕过去。
- 输出中涉及领域概念时使用 `CONTEXT.md` 的词汇（**对外发布**、**极简线**、**不自足功能**），不要漂移到它标为 `_Avoid_` 的同义词。
- 官方的要求清单与来源已整理在 `.scratch/release-prep/` 下的调研文件里，含原文引用与链接——需要判断某一条是不是硬线时，先看那里，不要凭印象。
- **本机的发布前提**：WP-CLI 与 Theme Check 插件都已装好，命令是 `wp theme-check run <主题>`，调用要给 `--path`。**打包不用 WP-CLI**（见 Implementation Decisions）。
- **Theme Check 基线（2026-10-16，对「打包后的样子」跑）**：REQUIRED 5 条——`wp_link_pages` 缺失、`readme.txt` 缺失（本件主动不要，见 ADR 0002）、截图缺失、`Author` 缺失、`Tested up to` 缺失。后四条本件做完即消，**只剩 `wp_link_pages`**。另有 WARNING 1 条（无版权声明）、RECOMMENDED 若干（编辑器样式、区块支持、对齐与图注的 CSS 类、`<title>` 硬编码、`Theme URI`/`Author URI`）、INFO 若干（`style.css` 的 `minimal` 标签不对、`light`/`dark` 已弃用、comment-reply 脚本未检出）。
- **演示内容**：截图需要几篇带缩略图的文章；dev 环境里现有什么，开工时先核，太空就先造。造数脚本要写明它改了哪些全站设置——本地环境是所有会话共用的。
- 这一件会**牵出下一件**：Theme Check 的 RECOMMENDED 里，「前台呈现与编辑器对齐」（编辑器样式、区块支持、对齐与图注的 CSS 类）是一类真缺陷，但属于设计工作，不在这件里。它和先前记下的「主题没有 `theme.json`」是同一件事。
- 修那两处缺陷会碰到**文章模板**与 `inc/comment-deletion.php`——都不在 `AGENTS.md` 的共享文件清单上，所以这一件仍然不与**评论提交不刷新**撞车（那一件动的是 `functions.php`、`comments.php`、`assets/js/`）。
