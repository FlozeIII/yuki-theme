# 02: 首页截图

**What to build:** 主题顶层多一张 `screenshot.png`——**真实渲染**出来的首页，浅色形态。它要能回答「这主题长什么样」：一屏里有圆点纹理的头部、纵向文章列表的节奏、左 112×84 的缩略图。它是真实页面，不是拼的营销图，所以既不撞官方「不得像广告」那条，也不会与实物不符。

浅色是主题的默认形态。深色很上镜，但它是变体——拿变体当门面，会让第一印象与装上之后的默认对不上。

这条能力加在**既有的无头浏览器共用件**上（给它补一只眼睛，不是新建 seam）。截图必须在设好视口之后产出，**不能**用 `msedge --screenshot --window-size` 那类老办法：那个按更宽的默认布局渲染再裁剪，看着像横向溢出，本仓库已经踩过一次。

**Blocked by:** 无（可以立刻开始）

**Status:** ready-for-agent

实现与验收已完成（起点 `ca5b9a8`）。

- [x] 仓库顶层有 `screenshot.png`，是 PNG，1200×900（4:3）
- [x] 它是一张真实渲染的页面，不是纯色、不是空白
- [x] 拍的是**首页**、**浅色**形态
- [x] 拍摄时页面上有真实内容：若干篇带缩略图的文章
- [x] 截图在设好视口之后由无头浏览器产出，不是 `--screenshot --window-size` 那类裁切法
- [x] 截图能力加在既有的浏览器共用件上，没有新增 seam

## Comments

### 实现与用法

```bash
node tests/bin/make-screenshot.mjs                       # 产出仓库顶层的 screenshot.png
node tests/bin/verify-screenshot.mjs                     # 验收（15/15）
php tests/bin/screenshot-fixtures.php <wordpress目录>    # 演示内容——重拍前先跑这条
```

重拍是**两步**：先造演示内容，再截图。README 的「重拍首页截图」一节写了这三条命令。

- **截图能力加在既有的共用件上，只增不改。** `tests/bin/browser.mjs` 里 `newPage()` 返回的页面对象
  多了一个 `screenshot()`（CDP `Page.captureScreenshot`，`captureBeyondViewport: false`），
  外加用法注释里的一行。既有的 `setViewport` / `goto` / `evaluate` / `measure` / `launch` **一行没动**，
  没有新增 seam。
- 「首页第一屏是什么样」这件事——视口多大、一篇文章以哪些类名算、第一屏摆了哪几篇——抽在
  `tests/bin/homepage.mjs` 里，产图与验收共用一份（见下面「审查」第 5 条）。
- `make-screenshot.mjs`：起无头浏览器 → `setViewport(1200, 900)` → 打开首页 → 截图。
  配色走 CDP 的 `prefers-color-scheme = light`；临时 profile 里没有 localStorage，走的正是主题
  「跟随系统」那条默认分支。实测：`html class="light"`，body 底色 `rgb(253, 251, 247)`，
  就是 `--yuki-background` 的浅色值（深色是 `rgb(24, 24, 31)`）。
- 拍之前先守拍摄条件，任一不成立就报错停下、**不产出新图**（先写临时文件再 rename，与
  `harness.mjs` 同法，坏掉的那次不会毁掉已有的图）：首页模板在（`.yuki-hero.yuki-dot-pattern`）、
  文章 ≥ 3 篇、视口里有带缩略图的文章、视口里的图都加载完了（等 5 秒，超时算失败）、
  页面落在浅色形态。拍完把第一屏的标题打出来——图里是什么，输出里就说什么。
- `screenshot-fixtures.php` 造演示内容：6 篇像正常博客的文章（分类是「生活随笔 / 前端笔记 / 读书记录」）、
  6 张柔和渐变的封面。**为什么要造**：首页当时只有别的工单留下的验证数据——标题带
  `YUKI-DENSITY`、摘要里写着 `YUKI-DENSITY-POST-EXCERPT`、缩略图是写着字的占位图。那是验证站的
  常态，但它是主题对外的一张脸。
- 演示文章**置顶**。光按日期排不够：这个本地站同时开着别的会话，它们的造数日期更新。实测第一次
  拍的时候，另一件工单（03）的分页测试文章就挤到了第二位——`YUKI-PAGEBREAK-TEST post paginated smoke1`
  夹在两篇演示文章中间。置顶之后 WP 把演示文章整体挪到首页列表最前，别的东西进不来。

### 验证

`node tests/bin/verify-screenshot.mjs`：**15/15 通过**。断言只认产物：文件级的事实（PNG 魔数、
IHDR 里的尺寸、4:3）从字节里读，画面级的事实（纯色与否、底色、有没有字与缩略图）把图当普通
图片加载进无头浏览器、画到 canvas 上读像素。生成脚本换写法这些断言不该红，产物变了一定红。

最后一节把**现在的首页**在同一视口下重渲染一遍。它不是重拍比对——页面上有日期、别的会话还在改
内容，逐像素比对必然抖——而是确认拍摄条件还在，并且**实时的 body 底色与图里读到的底色是同一个值**。
后一条把产物与当前的浅色主题钉在一起：拿一张深色图冒名顶替，这条会红。

变异表（把故意做坏的图喂给同一个验收脚本，用它的图路径参数，全程不动产物）：

| 变异 | 红在哪 |
| --- | --- |
| 删掉 `screenshot.png` | 截图文件在 |
| 纯色 1200×900（浅色底） | 不是一块纯色（1 种颜色）、有文字（0 点）、有彩色块（0 点） |
| 1000×900 | 尺寸、宽高比（外加内容三条：画面上只有两个字） |
| 非 PNG（文本文件改了名） | PNG 魔数、尺寸、宽高比、画面解不出来（报告照常打完，不崩） |
| 深色形态截图 | 占比最大的颜色是浅色底、不是深色形态、实时底色与图里不一致 |

完整回归串行执行一次：**11/11 退出码 0，447 条全绿**。

    29（基建）+ 34（防垃圾）+ 53（嵌套）+ 38（删除）+ 33（待审）+ 63（点赞）
    + 46（一言）+ 49（说说）+ 43（说说版式）+ 44（打包）+ 15（本件）= 447

11 份脚本各自串行跑一遍，完整输出在被 ignore 的 `.scratch/release-prep/02-regression-results.log`。

`verify-screenshot` 那 15 条验的是仓库顶层那张**现成产物**，不是当轮重拍的——它本来就不产图
（见上面「验证」一节）。那轮验到的产物是 mtime `19:30:49`、sha256 `291e9833…`，记在回归日志里；
它落在这一轮的窗口内（19:29:50 起），但**谁跑的那次 `make-screenshot.mjs` 我没法从时间戳上认领**，

### 审查

一个独立审查代理按起点 `ca5b9a8` 看了这份改动，报 6 项，逐条处理：

1. **`yuki_demo_category()` 把 `WP_Error` 读成 `term_id` 0。** 已修：建分类失败（例如同名的分类
   已经存在、只是 slug 不同）就写 stderr 并退出 2。原先会静默把文章丢进「未分类」——图看着没问题，
   分类徽章却是错的，正是那种「拍出来才发现」的错。
2. **量首页那一段没包在 try 里。** 站没起来时它会抛栈，一条断言都不打。已修：两个观察点各自容错，
   量不到就各报一条红（「画面能在浏览器里解出来」/「首页能量到（本地站已跑起来）」），报告照常
   打完、退出 1。实测把 `YUKI_SITE` 指到一个没人监听的端口：11/15，红在「首页模板在」「第一屏有
   缩略图」那几条上，没有崩。
3. **README 里那条 `php …` 照字面跑不起来。** 这台机器上没有系统级的 `php`，而 `YUKI_PHP` 是
   `lib.mjs` 读的变量、不是 shell 认的东西——原来那句括注等于没给可跑的命令。已修：README 写成
   便携版全路径，并注明路径见 `tests/README.md` 的环境变量表。
4. **`gmdate( strtotime( current_time() ) )` 是时区双跳。** 它算得对，靠的是「WordPress 把 PHP
   默认时区钉成 UTC」这一条——两个偏移正好抵消。已修：改用 `wp_date()` 直接按站点时区格式化，
   没这层依赖。改完重跑，还是 10 篇、第一屏顺序不变。
5. **选择器与视口在产图和验收两份脚本里各写了一遍。** 已修：抽成 `tests/bin/homepage.mjs`
   （`VIEWPORT` / `MIN_POSTS` / `READ_FIRST_SCREEN` / `measureFirstScreen`），两边共用一份。
   抽出来的理由与 `theme-css.mjs` 相同：写两遍，主题改个类名就会「产图按 A 判、验收按 B 判」。
6. **清理循环连附件也调了 `unstick_post()`。** 已修，顺带修掉一个更大的问题：附件原先只按标记 meta
   找，而标记是后加的——之前几轮建的附件一直没被清掉。现在附件改按**文件名前缀**单独清一轮
   （附件本来就不会置顶，不 unstick），把积下的 24 个孤附件一次清干净了。现在每轮稳定清 12 项
   （6 篇文章 + 6 张封面），不会再累积。

改完复核：`verify-screenshot.mjs` 15/15，变异表逐条仍然按要求红（纯色 3 条、尺寸 5 条、非 PNG 6 条、
深色 3 条、文件不在 1 条）。

### 刻意的取舍

1. **演示内容是写进共享库的**——6 篇文章、3 个分类、6 张封面附件，每个都带 `_yuki_screenshot_demo`
   标记，并且置顶。代价：这批文章会一直占住共享站首页的第一屏，直到重跑造数脚本（会先 `unstick`
   再删，连附件一起清，所以不会一轮轮攒附件）。换来的是「重拍一次就得到一张能交出去的图」。
   **theme mod 一处未改**（没有 `set_theme_mod`：站名、描述、每页文章数、`yuki_shuoshuo_category`
   都没碰）。唯一落到 option 表的是 `sticky_posts`——置顶本来就存在那里，它记的是「哪几篇置顶」，
   是逐篇文章的状态，仓库里 `shuoshuo-fixtures.php` 早就在用这套，清理时也按它的规矩 `unstick_post`。
2. **重拍要两步**，没有把造数并进截图命令。并入的话「拍张图」会顺手改别人的站，太意外。
   代价是忘了先跑造数就会拍到别的会话的验证数据——所以 README 写明顺序，且截图命令会把第一屏的
   标题打出来，眼看就知道拍到了什么。
3. **验收脚本接一个可选的图路径参数**（默认仍是仓库顶层那张）。加它是为了让上面那张变异表能在
   **不碰产物**的前提下跑——否则验「这些断言灵不灵」就得反复替换真正的产物文件。
4. 「不是纯色 / 不是空白」用像素统计判（颜色种数 ≥ 200、暗像素 ≥ 500、彩色像素 ≥ 500），
   阈值取得很松。这几条抓的是「一张纯色或空白的图」，不是去度量设计；真正紧的是底色那两条——
   直接跟 `--yuki-background` 的两个值比字符串。
5. **这张图拍的是当时的工作树。** 拍的时候同时开着别的会话，工作树里躺着它们的未提交改动
   （评论提交不刷新那件动的 `functions.php` / `comments.php` / `assets/js/comment-submit.js` /
   `inc/comment-submit.php`，Theme Check 两处缺陷那件动的 `inc/comment-deletion.php` / `page.php` /
   `single.php`）。已逐条看过：它们都是评论区与文章模板的事，**没有一处落在首页的呈现上**；
   首页相关的文件（`index.php`、`style.css`、`header.php`、`footer.php`、`template-parts/`）
   在 HEAD 与工作树里逐个一致（`git diff --name-only HEAD -- …` 为空）。所以这张图与 HEAD 的首页
   渲染一致。发布前若首页样式再动过（工单 04/05），要按 README 的两步重拍。
