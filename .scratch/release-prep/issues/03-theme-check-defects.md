# 03: 主题里 Theme Check 报出来的两处真缺陷

**What to build:** 两处使用者能撞上的缺陷。它们不是为过审而做的仪式，是体检筛出来的真东西——也是这一件里唯一动到主题代码的地方。

**其一**：文章用分页标记切开时，读者拿不到指向后续页的链接，**第二页够不着**。这是官方检查报的 REQUIRED 项。

**其二**：评论删除的确认页硬写了一个 `<title>`，而主题明明已经声明了标题由核心统一产出。结果是那一页绕过了主题自己的规则——标题该在哪儿生成，从此有了两处答案。

**Blocked by:** 无（可以立刻开始）

**Status:** ready-for-agent

- [x] 一篇用分页标记切开的文章，页面上出现指向后续页的链接，点得进去
- [x] 没有分页标记的普通文章不会因此多出一块空的翻页区
- [x] 打开评论删除确认页时，标题仍然正确显示
- [x] 确认页产出的 HTML 里**只有一个 `<title>`**
- [x] 主题其余页面的标题行为不变

## Comments

实现：`single.php`（正文之后加 `wp_link_pages()`）、`page.php`（同一处）、
`inc/comment-deletion.php`（标题改由核心产出）。
验收：`node tests/bin/verify-theme-check-defects.mjs` —— **33/33 通过**。
造数：`tests/bin/theme-check-defects-fixtures.php`（分页/不分页的文章与静态页面各一份，跑完按 id 精确清掉）。

### 其一：第二页够不着

`single.php` 里 `the_content()` 之后补一句 `wp_link_pages()`。核心这个函数在
`$multipage` 为假（正文里没有分页标记）时**自己什么都不输出**，所以「普通文章不会多出一块空的翻页区」
不是靠加条件判断换来的，是核心的既有行为——验收脚本把它单列了一条断言看住。

三处取舍：

- **用核心默认的包裹与文案**（`<p class="post-nav-links">Pages: …`），落在 `.yuki-prose` 里，
  段落间距与链接配色跟着正文走。没有另外配样式：那要动 `style.css`，而它是 `AGENTS.md`
  点名的共享文件；这一件按规矩不去碰它。代价是翻页链接看起来就是正文里的一行，没有
  `.yuki-pagination` 那种胶囊按钮的观感——要改是设计工作，与「第二页够不着」是两件事。
- **不新增任何主题自己的可翻译字符串**，所以 `languages/yuki.pot` 不用重新生成（它是发布用的
  生成物，多一条字符串就要按 `AGENTS.md` 第 5 条从 HEAD + 自己的改动重建一次）。
  代价是看到的是核心那句「Pages:」——本地站点是 en_US，中文站上核心会自己给出译文。
- **顺手也补了 `page.php`。** 工单正文说的是「文章模板」，但静态页面的正文一样能被分页标记切开
  （`$multipage` 由正文决定，与文章类型无关），缺陷是同一个。`$multipage` 是假时不输出，
  所以没分页标记的页面同样不受影响——验收脚本对页面也各验了这两条。

### 其二：确认页那个硬写的 `<title>`

删掉那行，改叫 `yuki_comment_delete_document_title()`：它先用 `pre_get_document_title`
把本页的标题文本（就是已经在用的那三个状态文案）报给核心，再叫 `_wp_render_title_tag()`
把它打出来——那正是 `wp_head()` 里打这一行的同一个函数。于是标题标签在主题里只剩一处来源。

- 这一页刻意不走 `wp_head()`（不加载主题样式表、也不要页头页脚），所以不能靠 `wp_head()`
  顺手产出标题；`_wp_render_title_tag()` 是这种情况下让核心产标题的唯一入口。
- 代价得认：那个函数在核心文档里标着 `@access private`。自己拼 `echo '<title>…'` 是公开 API，
  但那样主题里就又有了一处硬写的标题——正是这一件要拆掉的东西。函数注释里写明了这条取舍。
- 用 `pre_get_document_title`（短路）而不是 `document_title_parts`：这一页背后是首页那次查询，
  走后者核心还会往标题里接上站点描述，得再清一次才干净。
- **注释里一个尖括号都没写**：官方那一条是逐文件 `strpos( '<title>' )`，注释里出现一次也算数。
  这条不是我猜的——验收脚本的静态那一条第一版就是红在我自己写的注释上。

### 跑这轮时撞上的一件事

本机环境是几个会话共用的。更早那一轮里 `verify-comment-likes`（54/63）与
`verify-shuoshuo`（40/49）变红，红的形状都是「页面上什么都没有」（点赞控件位置 -1、各归档 0 条），
而当时另一个会话正在把主题临时换掉做自己的验收；同一环境各重跑一次就 **63/63、49/49** 全绿，
而这一件只碰了正文之后的翻页链接与确认页的标题，与点赞、说说归档无关。上面那轮干净的
465 条是重跑的记录。

为此在验收脚本的首尾各加了一条前提断言（站点跑的是本主题）：环境串了的时候，红的会是这一条，
而不是一堆看着莫名其妙的页面断言。

## Review

`/code-review` 对本次改动跑了 8 个角度（审查范围限定在本件这几个文件：工作树里有别的会话
尚未提交的 `comments.php`、`functions.php`、`tests/bin/lib.mjs` 等）。报回 5 条，处理如下。

### 改掉的（4 条）

1. **分页链接上的 HTML 实体没还原**（`verify-theme-check-defects.mjs`）。`esc_url()` 把查询串里的
   `&` 写成 `&#038;`，属性再编码一层就是 `&amp;#038;`；照原样请求，纯固定链接（`?p=123&amp;page=2`）
   那种地址会当作一个不存在的参数请求，拿回来的还是第一页——红的是「第二页没渲染出来」，
   而毛病在测试自己。本机是 `/%postname%/`，没有 `&`，平时不显形。已加实体还原。
2. **`fetchUrl()` 没兜住网络异常**。注释说它防的是「一个坏地址毁掉整轮」，但它只挡了空地址，
   `get()` 超时照旧抛出去——那样后面的断言一条都打不出来，收尾清理也不跑（共用环境里更糟）。
   现在连不上/超时都收敛成一个 `status: 0` 的失败壳。
3. **标题不再转义**。原来那行是 `esc_html( $titles[$state] )`，改成核心渲染器之后是原样 echo。
   三个字符串走翻译域，译文里带 `&` 或尖括号时不该比页面上那个 h1 少一层转义。已在过滤器里
   `esc_html()` 回去。
4. **造数按「同一身份就地更新」会在两个会话之间互相改内容**。甲读到的页面可能是乙刚写进去的
   RUN，于是「第一页只有第一页那段」红得莫名其妙。已改成**每次新造一篇**，收尾按这一轮拿到的
   id 精确清理（不按标记大扫除——同一条环境上别的会话正在用的那几篇不该被删）。

### 看过但保留的（1 条）

- **`_wp_render_title_tag()` 是私有的，没有兜底**。这条是明知而取：兜底要么得把硬写的标题标签
  请回来（正是这一件要拆掉的东西），要么在拿不到渲染器时**静默**少一个标题——按本仓库
  「默默跳过就是包错了但没人知道」的立场，静默比响亮更差。另外「主题不再声明 title-tag」这一支
  本来也不只是这一页的事：`header.php` 的 `wp_head()` 同样靠它产出标题，关掉就是整站没标题。
