# 02: 回复也一样，落位到被回复的那条下面

**What to build:** 回复某人时提交，我那条回复出现在**被回复的那条下面**——不是无脑追到列表末尾去。这件事在深层回复被压平之后尤其要紧：缩进说明不了「这条在回谁」，全靠那枚「回复 @谁」。

提交完之后，那个回复表单要**回到页面底部的原位并清空**，不能继续挂在别人的评论下面——那条评论刚多了一条回复，表单却还赖在那儿，看着像有份没交的草稿。回位直接调核心 comment-reply 脚本自带的取消回复，别自己搬 DOM。

新回复**不在视野里**时，页面把它带进视野；**已经在视野里**就什么都不做。不要无条件照搬没脚本那条路的跳转——它滚是因为整页重载后人已经不知道滚到哪儿了，那是重载的补偿，不是设计意图。

## Comments

### 一件本工单没写、但绕不过去的前提

**主题原来根本没排核心的 `comment-reply.js`。**

回复入口是 html5 形状的锚点（带 `data-commentid` 等属性、没有 `onclick`），而核心只让**区块**与
theme-compat 去排那个脚本（`wp-includes/blocks/comments.php:82` 那几处）——经典主题不排。所以以前
点「回复」是**整页跳到 `?replytocom=N`**，由核心在服务端把表单的父评论填好。那条路是通的，所以一直
没人发现；但这一件的前提（「表单先搬到被回复的那条下面，提交完再回原位」）在那条路上无从谈起，
本工单里那句「回位直接调核心 comment-reply 脚本自带的取消回复」也预设了它在页面上。

所以这一件把它排上了：`yuki_comment_submit_script()` 把 `comment-reply` 写进脚本依赖。**没有脚本时
那条路照旧**——锚点的 `href` 一个字没动，验收里专门有一条钉住它。

顺带说清楚：那个脚本**没有对外开 `cancelReply()`**（`window.addComment` 只导出 `init` 与 `moveForm`），
所以「调它自带的取消回复」只能是点那个取消链接——点击处理是它绑的，锚点的默认行为已经被它拦掉，
点它不会跳走。

### 实现

- **落位由服务端说了算。** 端点回话里多一个 `parent`：这条评论在**显示层级**上该挂在谁下面
  （0 表示最外面那一层）。脚本照着它插，自己不判第二遍——「深于两层的回复压到第二层」那条规则
  现在叫 `yuki_comment_display_parent()`，列表压平（`yuki_comment_flatten()`）与端点共用这一份。
  三处各写一遍的话迟早会判岔，而判岔的时候两边看起来都对。
- **那一段 HTML 的层级要真的对。** `yuki_comment_render_one()` 改成直接调
  `Walker_Comment::display_element()`，把「它挂在第几层」当入口参数喂进去。走 `wp_list_comments()`
  不行，两件事：
  - 一个带 `comment_parent` 的元素**不进** `$top_level_elements`，`wp_list_comments()` 对它什么也不画
    （回复会渲染成空串）；要让它认，就得连它挂上去的那条一起喂进去，再把属于新评论的那截从字符串里
    抠出来。
  - `depth-N` 是 `start_el()` 自增之后写进全局 `$comment_depth` 的（`class-walker-comment.php:177`），
    而这一条该在第几层，服务端已经算好了。
  所以传 `$depth - 1`。列表参数也因此补上了 `max_depth`（走 `wp_list_comments()` 时那一步由它自己填，
  绕开它就得自己写，且两边必须同值）。
- **标在「真正回的那条」上。** 回丙（丙显示上被压到第二层）时，新回复挂到甲下面，但那句仍然是
  「回复 @丙」——`yuki_comment_reply_to()` 读的 `comment_parent` 正是它真正回的那条。
- **脚本这一侧**：`insert()` 有了落位版（挂到父评论的 `ul.children` 里；没有就建一个，并给父评论补上
  服务端渲染时会有的 `parent` 类）；新贴进来的那一段里也有「回复」入口，而核心的 comment-reply 是按
  逐个链接挂事件的，所以调它留的那个入口 `window.addComment.init(inserted)` 补挂一遍；
  `endReply()` 点取消链接让核心把表单搬回去；`reveal()` 只在**不完全在视野里**时带一下。
- **滚动要等布局落定再决定**（两帧）。贴评论、把表单搬回页尾都会改页面高度，浏览器还要在下一帧做一次
  滚动锚定的补偿——当场量出来的位置，等补偿完就不作数了。这一件实际踩过：回复被判成「本来就看得见」
  于是不滚，而表单搬回去之后它已经在视野外面。

覆盖（这一件新加的）：三种情形的落位——回最外面那条、回第二层那条、回被压下来的那条——各自的
`parent`；那一段 HTML 的 `depth-2`、只有新的一条（没把挂上去的那条也带出来）、以及「回复 @谁」标的是
**真正回的那条**；**回一条页面根本不会显示的评论时如实拒掉**；真浏览器里点「回复」表单搬到那条评论
下面、提交后落在它的 `ul.children` 里、**没有**被追到列表末尾、表单回到页尾并清空、页面没有重载；
刚贴进来那条上的「回复」也是活的（核心的 MutationObserver 干的）；**换一次页面再看，它落在同一个
地方**（就地画出来的与服务端渲染的是同一件事），这一条对「被压到第二层」那种也单独验了一遍；
从 `?replytocom=` 进来的那条路（核心在服务端填好父评论、comment-reply 完全没参与）也照常落位，
而且**父评论会被清掉**（不清的话下一条评论会悄悄又变成一条回复）；滚动两种情况——已经在视野里时
脚本一次都没滚（数的是 `scrollIntoView` 的调用，不是 `scrollY`：搬表单本身就会让浏览器做锚定补偿，
那个不算脚本滚），离得很远时滚了一次并且看得见它。

## Standards

两个独立审查代理按 `7d309dd` 起点审查本件暂存路径（只审这五个路径）。规范轴 **2 项 P2、4 项 P3，无 P1**，
工单轴 **0 项未解决**（它指出的「工单没有 Comments」当时还没写，就是这一节）。两条 P2 都改在实处：

- **P2（注释说错了）** 我给「为什么不走 `wp_list_comments()`」写的理由是「一个带 parent 的元素不进
  `$top_level_elements`，那条回复就渲染成空」。**这是错的**：`Walker::paged_walk()` 末尾有一条「孤儿」
  分支（class-wp-walker.php:399-406），照样把它画出来，只是以 `$depth = 0` 进去、**印成最外面那一层**。
  真正的理由只有「层级得是入口参数」那一条。已经改直，并写明这一句先前是错的——照错的看代码的人会以为
  可以换回去。
- **P2（两条路会算岔）** 端点上溯走数据库，列表那边只看当前这一页取出来的评论。凡有一个祖先不在可见
  集合里，两边就算出不同的层级。已修，而且修的过程里**把平台真正的行为搞清楚了**（见下）。

工单轴另指出：`addComment.init(inserted)` 是多余的、`inc/comment-submit.js` 里那句「新来的它不认得」
也是错的——核心的 comment-reply 自己在 `document.body` 上装了 MutationObserver
（`comment-reply.js` 的 `observeChanges()`／`handleChanges()`，注释里就写着「comments loaded late」）。
那次手动调用已删（它还每调一次就把取消链接与表单的键盘处理再绑一层）。**顺手发现**：从 `?replytocom=`
进来时核心的取消没有落点（它要的占位元素不存在），父评论会留着——下一条评论会悄悄又变成回复。已修
（那种情形下父评论由我们清掉）并加了验收。

P3 也都改了：浏览器那几段的编号还写着 9x（外层的段落已经是 10）；「只有新的一条」那条断言名字比它验的
东西响（现在真的数 `<li>` 的个数并核对 id）；`onScreen`/`inViewport` 两个判据的区别写清楚了；滚动那两段
的取景与判据按审查的意见调稳。

## 这一件最值钱的一处发现

**「父评论不可见」的评论，页面根本不会显示——不是「显示在最外面那一层」。**

我原本按 `Walker::paged_walk()` 那条孤儿分支推断它会平铺着画出来（审查代理也是这么读的），据此先写了
一条断言「回它就该落在它自己下面」。跑起来是红的——那条评论**压根不在页面上**。查下去才看清：
`comments_template()` 在把评论交给 walker 之前，会按「最外面那一层 + 各自的子孙」**重建一次树**
（comment-template.php:1461 把 `hierarchical` 设成 `threaded`，1561-1576 做重建，子评论是另外查的）。
链子断了的那些（祖先待审、祖先进了回收站、祖先在别页）**整支都不在列表里**。

所以那一支根本没有「落在哪儿」的问题——收下来就是一条永远显示不出来的评论。处理办法与上一件里
「核心判成垃圾」那条一样：**如实说「没收下」**，表单退回去、写的东西留在手里。原生那条路此时是跳到
一个不显示它的地址上去，访客白跳一趟。

平台行为写进了 `inc/comment-submit.php` 的注释，出处标到行。
