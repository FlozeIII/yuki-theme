# 01: 提交之后页面不动，我那条评论就地出现

**What to build:** 写完一条评论点提交，**页面不跳走、不重载**，我那条评论就出现在列表里。

已公开的直接显示出来；还在待审的带着「等待审核」的标记，同时列表上方那句待审提示的**计数跟着加一**——不能出现「提示说有一条、列表里却看不见」这种自相矛盾。输入框清空，作者名与邮箱留着（靠 cookie 记住，和没脚本那条路一致）。提交进行中那个按钮点不动；网络出错时表单退回提交前的样子，我写的东西不消失。

**关键的一条**：两条路必须吐出**同一个结果**——同一条评论、同一个待审状态、同一封通知邮件。做法是让两条路压到核心的同一个评论提交函数上，由构造保证这一点，而不是靠两处代码各自记得做对每一件事。**那个函数不发评论作者 cookie，那是原生入口在成功后另做的**——端点必须自己补上，否则「待审评论对本人可见」会在这一条路上悄悄失效。

**没脚本的访客照旧能发评论**，那条路完全不动。端点公开、不校 nonce（与评论表单同一个理由）。别处正常入库的评论——通过 REST、XML-RPC、定时任务、导入脚本进来的——走它们自己的路，不受影响。

**Blocked by:** 无（可以立刻开始）

## Comments

### 实现与用法

代码全在**新文件**里：`inc/comment-submit.php`（端点、把落定那条渲染回 HTML、脚本的加载与配置）与
`assets/js/comment-submit.js`（增强脚本）。`functions.php` 只加一行显式 `require_once`、一处守卫范围
的改写，以及几个渲染辅助；`comments.php` 把三处「渲染什么」收成共用一份（见下）。

端点契约：

```
POST /wp-json/yuki/v1/comment-submit        （表单编码的正文，字段与原生入口一样）
200 { id, approved, html, heading, notice }  html 是列表里那一段评论，heading/notice 是列表页上那两段
4xx { code, message }                        message 为空表示「服务端什么也不说」，脚本就只把表单退回去
```

- **两条路压到同一个函数上**：端点调的就是核心的 `wp_handle_comment_submission()`，喂给它的是
  `wp_unslash( $_POST )`——与 `wp-comments-post.php` 交给核心的是同一份东西。「同一条评论、同一个待审
  状态、同一封通知邮件」是构造出来的，验收脚本也就真的抓了邮件来比对。
- **补上核心那个函数不干的一件事**：它不碰 cookie（那是原生入口在成功后另做的）。端点自己
  `do_action( 'set_comment_cookies', … )`，并把「记住我」那个勾选框的值一并交给它——**两条路对这个
  勾选框的处理因此也一致**（没勾就是清掉，不是不理）。
- **渲染走列表自己那套** `wp_list_comments( yuki_comment_list_args(), array( $comment ) )`，不另写一份
  评论标记。有一条踩过的坑写在注释里：`depth-N` 这些类来自 `Walker_Comment` 设的全局 `$comment_depth`
  （`wp-includes/comment-template.php:521`），所以**不能直接调 `yuki_comment_template()`**，否则每条都
  会被标成 depth-1。
- **防垃圾守卫差一点在端点上整个失效**。守卫本来放过所有 REST 请求（别的 REST 调用手上不该有蜜罐与
  令牌），而端点的回调里 `REST_REQUEST` 是定义着的（`wp-includes/rest-api.php:478`）——照原样跑，端点
  上填了蜜罐也照收。所以：守卫的判定范围改由 `yuki_comment_is_form_post()` 划，端点进处理前调
  `yuki_comment_form_post_declare()` 亮明身份。守卫的**判定本身**一个字没改。
- **三处「渲染什么」收成共用一份**：列表参数、评论计数那句「评论（N）」、待审提示那句。端点回话里带的
  就是列表页上那一份，脚本只负责替换——两边各写一份的话，措辞迟早会不一样，而两边看起来都对。
  验收脚本把「就地画出来的那句提示」与「刷新之后服务端渲染的那句」逐字比了一次。
- 「评论计数只在评论真的公开时才变」由服务端算好（核心的 `comment_count`，不含待审），脚本不做算术。

**本件刻意不做**（留给后面的工单）：

- **回复的落位**（02）。回复表单是核心 comment-reply 脚本搬过来的，脚本看 `comment_parent` 这个隐藏
  字段就知道自己在回谁——**非零就整页提交，完全照旧**。理由是这样哪条路都不会变差：把回复追加到列表
  末尾虽然也算「不刷新」，但缩进与位置是错的，而 02 正是来修这个的。代价是「没有重新加载」这条
  在回复上暂时不成立。
- **两种判定拆开**（03）。蜜罐与「太快」今天共用一个出口，端点也照原样只回一句没有话的拒绝；脚本
  收到空话就把表单退回去。把话说得更细是 03 的事。

**一处与原生那条路的已知差别**（不算违约，spec 里写明了端点不需要重定向）：没勾「记住我」时不发
cookie，原生那条路还会在跳转地址上挂 `unapproved` + `moderation-hash`，让本人 10 分钟内仍看得见。
端点不跳转，也就没有那对参数——本人**当场**看得见（就地在页面上），刷新之后要靠勾了「记住我」。
勾了的那条路两条完全一致（验收脚本两台路都验了）。

### 验证

`node tests/bin/verify-comment-submit.mjs`：**119/119 通过**。

红绿记录：端点还不存在时 42/78；补上实现后 75/84；把「回头客」的作者名也对上（核心那条 SQL 比的是
`comment_author` **加** `comment_author_email`，只对上邮箱不作数）后 84/85；补齐之后 86/86；
按两份审查的意见补上后面几段之后 119/119。

那次「明明实现了却还是红」值得记一笔：失败信息说「回话里成了 3」，而端点自己的读数是 2，看着像服务端
算错了。真相在**验收脚本自己**——`numberOf()` 取的是字符串里第一段数字，而 `<h3 class="yuki-comment-count">`
里就有一个 3，于是 `评论（2）` 被读成 3。更坏的是**失败信息与判断用的是同一个表达式**，所以它把
「结论」和「证据」一起带歪了。现在数字一律先剥标签再取（`htmlNumberOf()`），注释里写着这一条。

覆盖：端点正常／待审／蜜罐／太快／缺令牌／空正文六条回话；**核心自己判成垃圾的那一条**（命中「不允许的
关键词」→ 审批状态是 trash/spam、且**不是** WP_Error）与它该有的结局；两条路的状态与通知邮件一致性
（含「没勾记住我时两条路都不下发身份 cookie」）；待审评论**对本人可见**（带 cookie 看得见、不带看不见、
陌生人看不到）；「回复一条待审评论」与「回复一条压根不存在的评论」回话**逐字节相同**（不额外透露它存不
存在）；守卫范围的**四条入口**各一次探针（表单那笔提交照旧挡下；REST／XML-RPC／定时任务照旧放行）；
无脚本那条路的四种判定。

真浏览器七趟：待审那条就地出现 + 记号还在（没有重载）+ 提示计数加一 + 输入框清空而作者邮箱留着；
已公开那条让计数加一；请求在路上时按钮点不动、落定后又能点；把端点指到一个死端口时表单退回原样、
写的东西一个字没丢；填了蜜罐时页面上不多出一句话；**服务端说了话时那句话放到页面上**（空正文那条）；
**一篇文章还没有评论时列表与计数一起补上**（连次序一起验：计数那句排在列表前面）；
**核心判成垃圾时页面上什么也不画、输入框里的字留着**。

既有九份回归串行跑过一次：**388/388 通过**（防垃圾 34、待审 33、嵌套 53、删除 38、点赞 63、基建 29、
一言 46、说说 49、说说版式 43）。另两个会话新加的三份也顺手跑过：截图 15、缺陷修复 33、打包 44，
都全绿。

`tests/bin/lib.mjs` 的 `submitComment()` 加了一个 `target`（改投端点）：读真实表单那一套只该有一份，
两边各读一遍迟早会读歪，而读歪之后看起来仍然像「提交成功了」。

`languages/yuki.pot`：这一件**没有新增或删除任何字符串**，只把两条移了文件、几条行号变了。所以只更新了

### 一处刻意改了语义的地方

**待审提示数的是「这篇文章上一共有几条」，不是「这一屏上有几条」。** 原来那版数的是
`$wp_query->comments`（也就是当前这一页），端点那边没有「页」这个概念，两边要共用一份判断就只能取
整篇。列表分页时，提示会说到「总共有几条」，它不承诺这些评论都在眼前这一屏上——这句话是真的，而且
比原来那版更不容易少报。默认设置下（`page_comments` 关着）两者一模一样。这一条改的是原有行为，
所以在这儿点明，而不是埋在注释里。

### 已知的两处没做

- **那条错误提示没有样式。** `.yuki-comment-error` 是这一件新加的元素，`style.css` 里没有它、也没有可
  套用的颜色 token（设计系统里没有「危险」色，`DESIGN.md` 没定义过）。现在的样子是继承表单区的正文
  样式——能读，但不好看。要给它一个样子就是给设计系统加一枚颜色，那是 DESIGN.md 的事，不塞进这一件。
- **登录用户那条路验收没走到。** 端点为此做了一件事（登录用户带 `X-WP-Nonce`），但没有一条断言真的以
  登录身份提交过（要另搭登录的浏览器会话）。访客那条路是全覆盖的。

## Standards

两个独立审查代理按 `0798d5e` 起点审查本件的暂存路径（只审这一件的七个路径，另两个会话当时也在这棵
工作树上改别的东西）。

规范轴：**3 项 P2、5 项 P3，无 P1**。三条 P2 一条是行为缺陷、两条是注释说错了机制，都已修：

- **P2（行为）核心自己判成垃圾时端点会报成功。** 命中站点「不允许的关键词」时核心把审批状态设成
  `trash`/`spam`，而且**不给 WP_Error**（`wp-includes/comment.php:1384-1392`），所以那时只有
  `is_wp_error` 一道关会漏过去——一条垃圾评论会被画进列表，带着「看着发出去了、刷新就没了」的样子。
  现在端点在这种结果上如实说「没收下」（话留空，与守卫那两种判定一致），脚本把表单退回去。
  验收里加了 HTTP 与真浏览器两段钉住它。
- **P2（注释）** 说没带 nonce 的登录用户「会撞上 403」。核心的 `rest_cookie_check_errors()` 是把它**降级
  成匿名**（没有 nonce 时 `wp_set_current_user( 0 )` 然后放行），403 只在 nonce 在但无效时给。带 nonce
  仍然必要——真实的坏结果是登录用户被当成访客，而登录用户的评论表单没有姓名邮箱栏，于是收到一句
  「必填项没填」。注释已按真实机制重写。
- **P2（注释）** 错误映射那段说「核心给了状态码就用它自己的」，可代码把**挂在 200 上的**那几条校验错
  也落成 403（`require_name_email`／`require_valid_comment`）。代码是对的（脚本按 2xx 判成功），
  注释漏了这一桶，已补。
- P3 都修了：两处 core 行号指歪（`comment.php` 的 2113 与 153）、一句把 JSON 正文说成「会被照垃圾挡下」
  （真实机制是 `$_POST` 为空、在 `comment_id_not_found` 就拒了）、一个没用的 import、造数脚本头部
  「认邮箱」的说法（其实是作者名与邮箱一起认）。

规范轴同时逐条核了本件的核心引用（`REST_REQUEST` 在 `rest-api.php:478`；`wp_handle_comment_submission()`
不发 cookie 而 `wp-comments-post.php:55` 发；端点重发 `set_comment_cookies` 时签名与原生的完全一致；
守卫的 `WP_Error` 确实能穿过 `wp_new_comment(..., true)` 传出来），结论是都对得上。

工单轴：**0 项未解决的规范违反**，1 项 P2 与若干 P3。P2 就是上面「刻意改了语义的地方」——它指出的正是我
权衡过的那一点，结论是**把语义变更写在工单里**（而不是偷偷改），已照办。P3 里两条真的补了测试
（「列表还不存在」那条路、四条入口里的 XML-RPC 与定时任务），一条改了 spec 里与实现决定不一致的
用户故事（32 说的是「进出都是 JSON」，实际进去是表单字段），一条是「提示没样式」（见上方的
「已知的两处没做」）。

工单轴还指出一处我漏掉的结构问题：`launch()` 原先在 `try` 外面，无头 Edge 起不来时整份报告都打不出来。
现已按仓库既有的写法（`verify-comment-likes.mjs` 就是这么写的）把浏览器包进 `try`/`finally`，
起不来只记一条 FAIL。

复核结论：Standards 0 项未解决，Spec 0 项未解决。
