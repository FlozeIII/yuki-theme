# 04: 浏览器「太快 → 重试」场景不稳定

**What to build:** 把 `verify-comment-submit.mjs` 里「太快被挡 → 等 3.4 秒 → 再提交」这一段
变成确定性的验收，或者证明它抓到的是一个真实的产品竞态。

**已知表现（2026-10-17，发布后补丁 `f1887ed` 之后）：**

- 合并跑：`172/173`，评论插进去了，但 `.yuki-comment-error` 还挂在页面上。
- 单独复跑：`171/173`，第二次提交没有插进评论，页面上也没有错误框（没有那句话说出来的样子）。
- 两次失败方向相反，说明不是补丁的确定性回归。补丁的三处改动（令牌上界、`comment_post_ID`
  兜底要求、点赞限流）都不在这段场景的决定性路径上：
  - 令牌探针实核：签发后 4 秒 → `ok`；刚签 → `too_fast`；超一周 / 未来 → `missing`。
  - JS 走的是端点，端点在守卫前用 `yuki_comment_form_post_declare()` 亮明身份，
    不经过 `comment_post_ID` 那条兜底。
  - 注释里的顺序是 `say('') → insert(html)`，同一段同步代码里先收错误框再插评论。

**下一步的入手点：**

1. 在第二次提交那一趟抓服务端回话（HTTP 状态 + 响应正文），以及浏览器的网络事件——现在的断言
   只看到 DOM 的结果，看不到「到底是 4xx、空回话，还是 fetch 根本没回来」。
2. 若回话是 4xx 且 `message` 为空，查是哪一档判定走了静默（令牌、蜜罐、还是别的）。
3. 若是 fetch 没回来或超时，查共享 dev 环境里 PHP 内置服务器的单线程排队。
4. 修的是测试就修测试；若证明是产品竞态，按产品缺陷另立工单，不要在这里顺手改产品代码。

**验收：** 连续三次运行 `verify-comment-submit.mjs` 全绿，且断言能指出第二次提交的回话；
或者证明是产品竞态并另立工单。
