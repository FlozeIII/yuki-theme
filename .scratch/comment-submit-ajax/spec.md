# 评论提交不刷新

Status: ready-for-agent
Type: spec

## Problem Statement

访客写完一条评论、点下提交，**整页刷新**。他丢掉滚动位置、丢掉正读到哪儿，而评论区本来就在页面下方——一次提交等于一次小小的中断，对「写一句话」这件事没有任何好处。

更糟的是失败那两种情形。防垃圾守卫把提交挡下时，原生那条路给出的响应是**一片空白**：一位手快的真人（粘贴好一段话、两秒内点了提交）看到的是白屏，评论静静地没了——正是他重复提交、怀疑自己填错了的那个场景。

还有一件：**待审评论的去向**。提交之后他要么立刻在列表里看到自己那条（还带着「等待审核」），要么什么都看不到。这两者的差别决定了他是安心等着，还是再发一遍。

## Solution

把评论提交改成**页面不动、结果就地出现**，并且**不牺牲没脚本的访客**。

表单照原样留着——没有脚本时，整页提交那条路照旧能发评论。脚本能跑的时候，它接管提交，把结果就地画出来：新评论出现在它该在的位置（回复就落在被回复的那条下面）、待审的带上标记、列表上方那句待审提示跟着更新、表单回到原位并清空。新评论不在视野里才把它带进视野。

失败也被拆开来说话：机器人填了那个隐藏字段，静默丢弃，什么也不告诉它；**只是提交太快**（那可能就是个手快的人），页面给一句能照做的话——再点一次就成功了，因为那三秒窗口早过了。

两条路**必须吐出同一个结果**：同一条评论、同一个待审状态、同一封通知邮件。它们压到核心的同一个评论提交函数上，由构造保证这一点，而不是靠两处代码各自小心。

## User Stories

### 提交与结果

1. 作为访客，我希望点下提交之后页面不跳走，这样我不必重新找刚才读到哪儿。
2. 作为访客，我希望提交后**马上**看到结果，而不是整页刷新之后自己去列表里翻。
3. 作为访客，我希望我那条评论**就地出现在列表里**，而不是等下次刷新才看得见。
4. 作为访客，我希望还在待审的那条上标着「等待审核」，这样我知道它在这儿、但别人暂时看不到。
5. 作为访客，我希望列表上方那句待审提示**跟着更新**，而不是我刚提交完还写着「你有 0 条评论正在等待审核」。
6. 作为站点所有者，我希望**没有脚本的访客照旧能发评论**，这样不是所有人在我这里撞墙。
7. 作为站点所有者，我希望两条提交路径**吐出同一个结果**——同一条评论、同一个状态、同一封通知邮件。
8. 作为访客，我希望提交过程中有个明确的征兆，而不是点下去毫无反应。
9. 作为访客，我希望提交中那个按钮点不动，这样我不会连点两下发出去两条。
10. 作为访客，我希望网络出问题时表单退回提交前的样子，这样我写的东西不会消失。
11. 作为访客，我希望提交成功后输入框空掉，这样我不会看着旧内容以为没发出去。
12. 作为访客，我希望作者名和邮箱还留着，这样我再回一条时不必重填。

### 回复

13. 作为访客，我希望回复别人时，我那条出现在**被回复的那条下面**，而不是跑到列表末尾去。
14. 作为访客，我希望回复提交完之后，表单回到页面底部的原位并清空，而不是继续挂在别人的评论下面像个没交的草稿。
15. 作为访客，我希望新评论不在视野里时页面把它带进视野，已经在视野里时不要乱动。
16. 作为访客，我希望被压平的深层回复照旧标着「回复 @谁」，这样我看得出它在回谁。

### 失败态

17. 作为访客，我希望提交太快被挡下时页面**告诉我一声**（请再点一次），而不是给我一片空白。
18. 作为访客，我希望**再点一次就能成功**——那三秒窗口早过了。
19. 作为站点所有者，我希望机器人填了那个隐藏字段时被**静默丢弃**，且什么也不告诉它。
20. 作为站点所有者，我希望这两种判定**被拆开**——填隐藏字段是确定的机器人信号，提交太快只是个怀疑。
21. 作为访客，我希望被挡下时看到的那句话**不教我绕过它**。

### 一致与边界

22. 作为站点所有者，我希望「待审评论只对本人可见」在**两条路上**都成立——尤其靠提交那一刻发出的那枚 cookie。
23. 作为站点所有者，我希望评论计数只在评论**真的公开**时才变。
24. 作为访客，我希望禁用脚本时页面不报错、评论表单照旧完整可用。
25. 作为站点所有者，我希望新端点**公开、不校 nonce**——和评论表单同一个理由：开着页面缓存的站点上，硬加一个只会让正常访客莫名失败。
26. 作为站点所有者，我希望新端点**不额外透露某条评论存不存在**，别让人拿它当探查手段。
27. 作为站点所有者，我希望这套东西**不给别处正常入库的评论添堵**——通过 REST、XML-RPC、定时任务或导入脚本进来的评论，走它们自己的路。
28. 作为访客，我希望深色模式与窄屏下这套交互照旧好用。
29. 作为站点所有者，我希望**不引入账号体系**——**评论增强**的定义里明确不含注册、登录、找回密码。
30. 作为站点所有者，我希望这件事**不要求使用者做额外配置**。

### 维护

31. 作为维护者，我希望「页面没有重新加载」这件事**有条命令能验**，而不是只能靠眼睛看。
32. 作为维护者，我希望端点的输入与输出都有明确的形状——进去是**表单字段**（与原生那条路同一份），回来是 JSON，这样它能被脚本直接打。
33. 作为维护者，我希望这套断言只认**外部看得见的行为**，实现换了测试不该红。

## Implementation Decisions

### 形态

- **渐进增强**。表单的 `action` 仍然指向 WordPress 原生的评论提交入口；没有脚本时那条路完全照旧。
- 新增的前端脚本放**新文件**，只负责让提交不走整页刷新。它是增强，不是页面本身。
- 不引入构建步骤，不引入前端框架。新增脚本只能是能直接跑的原生脚本，与现有几个同级。

### 端点

- 新增一个公开的 REST 端点，形如 `POST /wp-json/yuki/v1/comment-submit`，请求体是**表单字段的形状**（与原生那条路交上去的一样），回话是 JSON。
- 端点内部调用**核心的那个评论提交函数**（`wp_handle_comment_submission()`）。两条路压到同一个函数上——「吐出同一个结果」由此成立，而不是靠两处代码各自记得做对每一件事。
- **必须补上核心那个函数不干、而原生入口干的两件事之一：发评论作者 cookie。** 核心函数不碰 cookie，那是原生入口（`wp-comments-post.php`）在成功后另做的。漏了它，「待审评论对本人可见」会在脚本这条路上**悄悄失效**——访客刷新后看不到自己那条，以为没发出去。
- 另一件是重定向，端点不需要：它回话给脚本，不跳转。
- 端点**不额外透露某条评论存不存在**。核心那个函数自己就会拒掉「回复一条还没公开的评论」（返回 403），端点上照它的判断回话即可——**不要为了给出更友好的错误而多说一句**，那会把端点变成探查评论是否存在的手段。
- 端点只适用于**表单型提交**那条调用路径。别处（REST、XML-RPC、定时任务、导入脚本）手上不该有这套表单协议，按机器人处理只会把别处正常入库的评论静默吞掉。
- 公开端点，**不校 nonce**。理由与评论表单一致（WordPress 自己的评论表单也不校，而开着页面缓存的站点上加 nonce 只会让访客莫名失败）。代价要说清楚：不带 cookie 的请求每次都拿到新身份，这挡的是手滑与刷新，挡不住刻意绕。

### 回话与呈现

- 回话里带上：落定的评论标识、它**待审还是已公开**、以及**服务端渲染好的那一段评论 HTML**。
- 脚本把那段 HTML 插到**正确的位置**：回复落到父评论的子列表下，不是无脑追到列表末尾。
- **不写第二份评论 HTML。** 评论的印记只在一处（列表渲染用的那个模板）——两处各写一份，迟早会漂，而漂的时候两边看起来都对。
- 待审的那条要带上它与已公开评论不同的标记，并且**列表上方那句待审提示的计数要跟着加**——不能出现「提示说有一条、列表里却看不见」这种自相矛盾。
- 评论计数只在评论**已公开**时才变。

### 表单与收尾

- 提交中禁用提交按钮；网络失败退回提交前的样子。照评论点赞那套先例（先乐观画、以服务端回话为准、失败退回）。
- 成功之后：表单**回到页面底部的原位**（调核心 comment-reply 脚本自带的取消回复，别自己搬 DOM）、输入框清空。作者名与邮箱留着——它们靠 cookie 记住，两条路一致。
- 滚动：新评论不在视野内才把它带进视野，用最小距离；已经在视野里就什么都不做。**不要无条件照搬原生那条路的跳转**——原生会滚是因为整页重载后人已经不知道滚到哪儿了，那是重载的补偿，不是设计意图。

### 失败态

- **把两种判定拆开**：填了隐藏字段（确定性机器人信号）→ 静默丢弃，不给可辨认的提示；提交太快（只是怀疑）→ 回一句可重试的话（意思就是「再点一次」）。
- **原生那条路也要同步改。** 它今天对两种判定都给一片空白，手快的人同样丢了评论。两条路结果不一致，比两条路都差还难查。
- 判定仍然发生在评论**入库之前**——垃圾不落库。这一条不动，也不进入待审队列。

### 明确不引入

- 不引入账号体系。
- 不要求使用者做额外配置。
- 不给待审评论增加任何入口。

## Testing Decisions

### 什么算一个好测试

只断言**外部可观察的行为**，不断言实现细节。

具体说：断言「填了隐藏字段的提交没有出现在页面上」，而不是「那个函数返回了 false」；断言「点提交之后 `window` 上那个记号还在」，而不是「脚本调用了 fetch」。实现方式换了、测试不该红；行为变了、测试必须红。

### Seam

**不新增 seam。** 还是那一个：**HTTP**。请求进去、HTML 出来——它一次性覆盖路由、模板层级、函数、转义，以及评论提交这类真正的写入路径。

新端点与无 JS 那条路都在这一层。另有两处 HTTP 够不着，用仓库**既有的**观察点补：

1. **无头浏览器观察点** —— 「页面没有重新加载」只有它看得见，而那是这一件的全部卖点。做法：打开文章页 → 往 `window` 放一个记号 → 触发表单提交 → 等回话落地 → 断言记号还在（页面若重载过，`window` 是新的，记号就没了）。顺带断言新评论的 DOM 节点出现、输入框空了。这**不是新 seam**——工单 03 与 08 已经在用同一个观察点量颜色和宽度，这次只是换上另一类断言。
2. **既有辅助 `submitComment()`** —— 它像浏览器一样提交：先 GET 文章页、从表单里取出**实际存在**的字段、等过判定窗口再 POST。无 JS 那条路的断言直接用它。

### 要测的模块

- 端点：正常提交、填了隐藏字段的提交、提交太快的提交——三条路各自的可见结果。
- 无 JS 那条路照旧能发出评论，且四种判定（正常、蜜罐、太快、缺令牌）表现与端点一致。
- 待审评论**对本人可见**：带上提交时发出的 cookie 再打一次，看得见；不带就看不见。
- 回复落到父评论的子列表下面，不是列表末尾。
- 提交成功后表单回位并清空。
- **页面没有重新加载**（浏览器观察点）。
- 待审提示的计数跟着更新。
- 网络失败时表单退回提交前的样子。

### 明确不测什么

- WordPress 自己的评论提交流程（那是平台的事）。
- 防垃圾守卫**内部**怎么实现的——只测它挡下之后**外面看到什么**。
- 核心的 comment-reply 脚本怎么搬表单的。
- 页面缓存与这一件的交互。

### 先例

一工单一脚本：`tests/bin/verify-comment-submit.mjs`，与现有几份同级。公共辅助从 `tests/bin/lib.mjs` 取；CSS 与浏览器那两处取 `theme-css.mjs` 与 `browser.mjs`。

## Out of Scope

- **评论的 Markdown 支持与表情选择器。** 上一轮 spec 已经否过：前者给渲染路径多一层解析器、安全面变大，后者要给主题打包资源，对个人博客不成正比。
- **站内注册、登录、找回密码。** 账号体系是另一件事。
- **评论列表的「加载更多」或无限滚动。**
- **把评论区的其它操作也 AJAX 化**——删除确认页、点赞都各有各的归属（点赞已经做完）。
- **改动评论的展示层级或版式。**
- **性能优化**（缓存、预取、把评论列表渲染搬去前端）。
- **一言与说说**，与这一件无关。

## Further Notes

- **共享文件警告。** 这一件会碰 `functions.php` 与 `comments.php`——**两个都在 `AGENTS.md` 第一条的共享文件清单上**。动手前先在 `.scratch/holds.md` 挂两行，提交后删掉。新的前端脚本放新文件，天然不冲突。
- **与「发布物料」那批工单不共享文件**，可以并行开工；但上面那两行 hold 各自要挂。
- 输出中涉及领域概念时使用 `CONTEXT.md` 的词汇（**评论增强**、**对外发布**、**不自足功能**），不要漂移到它标为 `_Avoid_` 的同义词。注意**评论增强**的定义已经把列举改成非穷尽，边界落在「不含账号体系」那条硬规则上——这一件正好落在里面。
- 核心那个评论提交函数**不做什么**，是这一件最容易出错的地方（它不发 cookie、不重定向）。实现时对着本机的 WordPress 源码核一遍，别凭印象。
- 「页面没有重新加载」必须有**一条真浏览器断言**钉住。这是唯一一处 HTTP 够不着、又恰是全部卖点的地方。
