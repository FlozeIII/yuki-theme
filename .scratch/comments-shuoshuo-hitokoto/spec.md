# 评论增强 · 说说 · 一言

Status: ready-for-agent
Type: spec

## Problem Statement

站点所有者可以用这个主题搭起自己的博客，但**还不能把它交给别人用**。

装上之后有三个地方撑不起一个真实在运营的博客：

**评论区不可用。** 现在只有裸的评论列表和提交表单，没有任何防垃圾手段——一旦开放评论，垃圾就成了待审队列里清不完的噪音。访客提交之后看不到反馈：评论要么立刻公开，要么静默消失，他不知道发生了什么，于是重复提交。深层嵌套回复在窄屏上会把内容挤成一条缝。评论区的样式也没有跟上主题其余部分（别处都走设计 token）。评论者与自己的评论之间没有关系：写错了删不掉，看别人写得好也没有轻量的表达方式。

**只有文章一种内容形态。** 想发一句短的想法，就得占用一篇文章的位置、混进首页列表——「文章」和「碎片」两种完全不同的节奏被搅在一起。站点所有者要么放弃发碎片，要么接受首页变得杂乱。

**站点是静态的。** 除了内容本身，页面上没有任何随访问而变化的东西。

## Solution

三件事，一起把主题补到「可以对外发布」的水准。

**评论增强**：让评论区成为一个能真实运转的评论区。用对访客无感的手段挡住自动提交；让每个访客都能看到自己那条评论的状态和去向；把回复层级收在一个手机上仍然可读的深度；让评论区用上主题的设计 token。再给访客两件他本来就需要的东西——给评论点赞，以及删掉自己写错的评论。全部不需要注册账号。

**说说**：给站点所有者第二条内容通道。一篇说说就是一篇普通文章，归入一个指定的分类；它不进首页的文章列表，但有自己的归档。数据是普通文章，换任何主题内容都还在。

**一言**：站点上露出一句随机的话。由服务端取回并缓存，访客不直接触碰第三方接口；第三方挂了就用主题自带的句子顶上，页面不会缺一块。

## User Stories

### 评论 · 挡住自动提交

1. 作为站点所有者，我希望评论表单带一个正常访客看不见也不会去填的字段，这样机器人的自动提交会被挡下，而不是变成待审队列里的垃圾。
2. 作为站点所有者，我希望表单带一个提交时间戳，这样页面加载后一瞬间就提交过来的评论会被判为机器人。
3. 作为站点所有者，我希望上述判定发生在评论入库之前，这样垃圾不会先落进数据库再等我去清理。
4. 作为站点所有者，我希望时间戳是防伪造的，这样机器人不能靠随便填一个值绕过它。
5. 作为访客，我希望正常填写不会被误判成垃圾，这样我不必重复提交或者怀疑自己哪里填错了。

### 评论 · 我自己那条评论的去向

6. 作为访客，我希望提交后看到「已提交，等待审核」这类明确提示，而不是页面静默刷新、让我不知道成没成。
7. 作为访客，我希望带同一身份再访问时能看见自己那条还在待审的评论，这样我不会以为它丢了而重复提交。
8. 作为站点所有者，我希望待审评论只对它的作者本人可见，这样我不必为了让他安心而提前公开它。
9. 作为站点所有者，我希望页面上告诉访客「审核通过后会出现在这里」，这样他知道接下来会发生什么。

### 评论 · 层级与样式

10. 作为访客，我希望回复最多嵌套两层，这样深层讨论在手机上仍然读得下去。
11. 作为站点所有者，我希望更深的回复被压平到第二层而不是继续缩进，这样不会出现一条越来越窄的缝。
12. 作为访客，我希望每一层都能看清谁在回复谁，这样我不必靠缩进去猜。
13. 作为站点所有者，我希望评论区的列表、表单、按钮全部使用主题的设计 token，这样它和文章页、侧边栏看起来是同一个主题。
14. 作为站点所有者，我希望深色模式下评论区配色正确，这样夜里读评论不刺眼。

### 评论 · 点赞

15. 作为访客，我希望给一条评论点赞，这样我想表示「同意」时不必再写一条内容重复的评论。
16. 作为访客，我希望看到每条评论的点赞数，这样我能快速判断哪条值得读。
17. 作为访客，我希望我点过的评论有视觉上的区别，这样我知道自己点过哪些。
18. 作为访客，我希望同一条评论只能点一次，这样数字不会被一个人刷上去。
19. 作为访客，我希望再点一次可以取消，这样点错了能收回。
20. 作为站点所有者，我希望点赞计数不因为刷新页面或换浏览器就失真，这样它还是个可信的信号。

### 评论 · 删掉我自己写错的

21. 作为访客，我希望提交评论后收到一封带链接的邮件，这样我以后可以自己删掉它。
22. 作为访客，我希望不必注册账号就能用这个链接，这样我不会为留一条评论而开一个账号。
23. 作为访客，我希望这个链接是一次性的，这样它被转发出去也不会让别人能删我的评论。
24. 作为访客，我希望链接会过期，这样它泄露很久之后也不会突然生效。
25. 作为访客，我希望打开链接时看到一个确认页而不是直接删除，这样误点不会造成损失。
26. 作为站点所有者，我希望访客只能删掉自己的评论，这样别人的评论不会被误删。
27. 作为站点所有者，我希望删掉的评论要么彻底移除、要么回到待审，而不是留下一个可见的空壳。

### 说说

28. 作为站点所有者，我希望发一条短内容而不占用文章的位置，这样首页保持「文章」的节奏。
29. 作为站点所有者，我希望用我已经熟悉的方式（分类）来标记它，这样我不必学一套新的编辑器界面。
30. 作为站点所有者，我希望说说不出现在首页的文章列表里，这样两种内容不会混在一起。
31. 作为站点所有者，我希望说说有自己的归档页，这样想一次看完的人有地方去。
32. 作为访客，我希望说说在归档里以更紧凑的形式呈现，这样短内容不会显得空旷。
33. 作为站点所有者，我希望在自定义器里指定用哪个分类承载说说，这样我不必接受主题硬编码的分类名，也不必改我已有的分类结构。
34. 作为站点所有者，我希望启用主题时若那个分类不存在就自动建一个，这样我不用手动准备。
35. 作为站点所有者，我希望删掉、改名或换 slug 那个分类时站点不会报错，这样我调整分类结构不会把站弄坏。
36. 作为站点所有者，我希望没有配置承载体时说说相关功能安静地不生效，而不是在页面上留下空白或错误。
37. 作为访客，我希望说完还能评论，这样碎片动态也能被回应。
38. 作为站点所有者，我希望停用或更换主题后这些内容都还在，即使归组没了。

### 一言

39. 作为站点所有者，我希望页面上露出一句随机的话，这样站点有一点随访问而变化的活气。
40. 作为站点所有者，我希望这句话由服务端取回并缓存，这样访客的浏览器不直接请求第三方，也不把我的访客的 IP 交给它。
41. 作为站点所有者，我希望缓存一小时，这样第三方不会被我高频敲打。
42. 作为访客，我希望第三方接口挂掉或超时时仍然看到一句话，这样页面不会缺一块。
43. 作为站点所有者，我希望兜底句子存在主题里、不依赖网络，这样最坏情况也是完整的。
44. 作为站点所有者，我希望不想用它的时候能关掉，这样它不会强加给每个人。
45. 作为站点所有者，我希望它的取回失败不会拖慢页面，这样我不必为它调服务器超时。
46. 作为站点所有者，我希望取回的内容经过转义再输出，这样我不会因为第三方返回了奇怪的东西而被注入。

## Implementation Decisions

### 通用约束

- **对外发布**是本轮所有取舍的前提：默认体验、向后兼容、不要求使用者做额外配置。
- 维持 `Requires PHP: 7.4` 与 `Requires at least: 6.0`。
- 不引入构建步骤，不引入前端框架。新增 JS 只能是能直接跑的原生脚本，与现有两个脚本同级。
- 不引入账号体系（**评论增强**的定义里明确不含注册、登录、找回密码）。

### 评论 · 表单与拦截

- 评论表单新增两样对访客无感的东西：一个伪装成普通字段的**蜜罐**，以及一个**时间戳令牌**。
- 令牌必须带签名，只有本站能签发，避免被随意填值绕过。
- 拦截发生在评论入库之前，不是入库后打标记。
- 判定窗口：从页面加载到提交短于 3 秒视为机器人。
- 蜜罐字段必须不出现在任何面向访客的输出里（包括评论列表），否则会被浏览器自动填充误伤。
- 被判定为机器人的提交按垃圾处理，不进入待审队列。

### 评论 · 待审可见

- 访客提交后，页面上给出明确的待审提示，而不是静默刷新。
- 待审评论对**其作者本人**可见（依赖 WordPress 原生的评论作者 cookie 机制），对其他访客不可见。
- 这条不新建身份机制，复用现有的匿名评论 cookie。

### 评论 · 层级与样式

- 嵌套层数上限 **2**。更深的回复压平到第二层，而不是继续缩进。
- 评论区的列表、表单、按钮一律改用设计 token，与主题其余部分一致；深色模式同步覆盖。

### 评论 · 点赞

- 计数存放在评论元数据里，按评论累加。
- 同一访客对同一条评论只能计一次：用站点 cookie 标识访客。这挡得住手滑和刷新，挡不住刻意清 cookie——对个人博客量级够用，不引入账号或 IP 存库。
- 再点一次取消，计数相应减一。
- 读写都走一个端点，不用页面刷新。

### 评论 · 删除自己的评论

- **不引入账号体系**：靠「评论时填的邮箱 + 一次性令牌」证明所有权。
- 令牌在评论成功提交后签发，随通知邮件发出；令牌本身存为评论元数据，带过期时间。
- 令牌一次性：用过即失效。链接必须过期，避免长期有效。
- 打开链接先到确认页，确认后才执行删除；避免误点（也避免邮件客户端预取链接就把评论删掉）。
- 只能删自己的：令牌与评论一一绑定，不可跨评论使用。
- 删除后的语义：彻底移除，或者回到待审——不留可见空壳。

### 说说

- **形态遵循 ADR 0001**：一篇说说就是一篇普通文章，归入一个**保留分类**。不注册自定义文章类型，不用文章格式，不用自定义分类法。
- 承载体分类由自定义器指定。默认 slug 用 `shuoshuo`，主题激活时若不存在则创建；但**不硬编码**——用户改名、换 slug、删除后主题必须安静地降级，不能报错。
- 承载体分类被删或未配置时，说说相关功能整体不生效，页面上不留空白或错误。
- 主列表（首页与博客归档）必须显式排除该分类；排除作用于主查询，不影响该分类自己的归档与其他查询。
- 说说的归档就是这个保留分类的分类归档，沿用现有归档模板；列表项走更紧凑的呈现，不复用文章列表那种大缩略图的版式。
- 说说仍然是普通文章，因此评论、搜索、feed 等都自然生效。

### 一言

- 取回在服务端进行，用一个一小时（1 小时）的 transient 缓存结果。
- 超时设置得短，取回失败不能拖慢页面渲染。
- **自带兜底**：主题内置一组句子，取回失败（超时、非 2xx、解析失败）时从其中取一句。这对应词汇表里的**不自足功能**——一言是本主题唯一依赖外部服务的功能，必须有降级。
- 第三方返回的内容必须转义后再输出。
- 放置方式：作为**侧边栏的内置默认小工具**之一。侧边栏已经支持「放了自定义小工具就接管、一个都不放则回退到内置默认」的机制，因此一言天然可关闭，不需要额外的开关。

### 涉及的数据

- 评论元数据：点赞计数、每位访客的点赞标记归属、删除令牌及其过期时间。
- 主题选项：承载说说的分类。
- transient：一言的缓存。
- 无自定义数据表。

## Testing Decisions

### 什么算一个好测试

只断言**外部可观察的行为**，不断言实现细节。

具体说：断言「填了蜜罐的提交没有出现在页面上」，而不是「那个函数返回了 false」；断言「深于两层的回复被压平」，而不是「某个参数被设成了 2」。实现方式换了、测试不该红；行为变了、测试必须红。

### Seam

**只有一个：HTTP。** 请求进去、HTML 出来。

这是能取到的最高一层，一次性覆盖路由、模板层级、函数、转义，以及评论提交这类真正的写入路径。这个仓库目前没有任何测试框架，新增低层 seam 会同时引入框架和与「无构建步骤」定位的冲突。

现有先例就是这一层的：HTTP 断言脚本 + 造数据脚本。新测试延续同一套，不引进 PHPUnit / Jest。

### 三件 HTTP 够不着的事，用测试基建设施补（不是新 seam）

基建设施不改变产品的任何接口，只是给本地环境装上观察点：

1. **删除链接在邮件里。** 本地站发不出邮件。用一个 mu-plugin 把 `wp_mail()` 的调用记到文件，测试读文件取出链接，再用 HTTP 打那个链接。
2. **一言的缓存与上游调用次数。** 把上游指向一个本地 stub，数命中次数——第一次命中上游、一小时内第二次不命中。
3. **一言上游故障。** 让同一个 stub 返回 500 或直接不可达，断言页面上出现的是内置兜底句而不是空白。

### 要测的模块

- 评论提交路径（蜜罐、时间戳、正常提交）——HTTP POST
- 待审评论的可见性——HTTP，带 cookie
- 评论输出层级——HTTP
- 点赞读写端点——HTTP
- 删除令牌的签发、一次性、过期、误用——HTTP + 邮件捕获
- 说说在主列表的排除与该分类归档的包含——HTTP
- 承载体分类缺失时的降级——HTTP
- 一言的取回、缓存、兜底、转义——HTTP + 上游 stub

### 明确不测什么

不测 WordPress 自身的行为（评论 cookie 机制、模板层级解析），那些是平台的事。只测本主题在这之上加的东西。

## Out of Scope

- **AJAX 提交评论**（不刷新页面）。第三档里的体验优化，改动面最大——要新建端点、前端脚本、错误态处理，并和待审提示联动。留到下一轮。
- **评论的 Markdown 支持**与**表情选择器**。前者会让渲染路径多一层解析器、安全面变大；后者要给主题打包资源。对个人博客不成正比。
- **站内注册、登录、找回密码**。账号体系是另一件事；删除自己的评论已用邮箱方案覆盖。
- **相关文章、友情链接、公告、PWA、内置 SEO**。按**极简线**属于线外。
- **头像**。已完成（**头像镜像**）。
- 自定义文章类型、配套插件、自定义分类法、文章格式作为说说的承载方式——见 ADR 0001。
- 说说的富媒体编辑器定制、批量导入、跨站同步。

## Further Notes

- **ADR 0001 约束着说说这一块的形态**，任何「改用 CPT 会更好」的想法都要先推翻它，而不是绕过去。
- 输出中涉及领域概念时使用 `CONTEXT.md` 的词汇（评论增强、说说、一言、极简线、对外发布、不自足功能），不要漂移到它明确标为 `_Avoid_` 的同义词。
- **对外发布**这一条会反复影响判断：任何要求使用者额外申请密钥、额外启用组件、额外配置服务器的方案，默认都不合格。
- 本 spec 覆盖三个功能，它们共享同一个 seam 与同一套测试方式。拆工单时允许出现跨功能的阻塞边（例如说说的呈现依赖承载体分类的配置）。
