# 08: 说说归档的紧凑呈现

**What to build:** 说说归档里的条目以更紧凑的版式呈现，不套用首页文章列表那种「大缩略图 + 摘要」的样式。一两句话的短内容在归档里不该显得空旷，并且一眼能和正式文章区分开。

只动说说归档，不影响其他归档页。

**Blocked by:** 04

**Status:** ready-for-agent

- [x] 只有一两句话的短内容在归档里不显得空旷
- [x] 分类、标签、日期归档的版式不受影响
- [x] 深色模式下版式正确

## Comments

实现：`866e5a3`。验证方式：`node tests/bin/verify-shuoshuo-density.mjs` —— **43/43 通过**。

**只动说说归档。** `archive.php` 的判据是 `is_category() && get_queried_object_id() === yuki_shuoshuo_category_id()`：
只有打开的归档**就是**配置的那个承载体分类时才换版式。承载体没配置、被删、id 失效时那个函数返回 0，
这段自然不生效；改名或换 slug 也不受影响（**按 term id 认，不按 slug**，见 ADR 0001 的影响一节）。
分类/标签/日期/首页/搜索/作者六种归档逐页断言过：仍是文章列表那套、带缩略图、没有紧凑版式的类。

**紧凑版式长什么样**：正文直接铺开（全文，不截摘要——说说的正文本来就短，摘一句反而把它掏空），
不取缩略图（造数刻意给每条都挂了图，就是为验它没被用上），标题一行、日期与评论链接一行弱化小字，
项间 1px 分隔线。深浅两色与窄屏都在真浏览器里量过。

**标题元素不论有没有标题都在。** 这条是代码审查揪出来的：原先没标题的条目整个不输出 `<h2>`，
屏幕阅读器靠标题层级跳读，那条会被跳过。现在标题元素常在，链接落在标题里（有标题时是标题本身，
没标题时是日期），于是每条恰好有一个带名字的链接；造数里专门留了一条无标题的说说走这条路。

**「不显得空旷」是量出来的，不是看出来的**：断言每一条的「高度 − 正文高度 − 元信息高度 − 上下内边距」
落在 0～30px（行高与外边距的余量）。也就是卡片里除内容之外没有多余空处。起初我拿「比文章列表条目矮」
当判据，审查指出那个对照不公平（文章条目的高度是缩略图撑的、且随文案长度翻红），现在它只作为参考数字
印在报告末尾，不再当断言。

六条各自落在哪里：

1. 版式不同：条目用 `.yuki-shuoshuo-item`、整页没有 `.yuki-post-item`、条目里没有 `<img>`。
2. 不空旷：上面那条「高度都说得清来路」的推导断言，逐条量。
3. 其他归档不受影响：六种归档逐页断言（见上）。
4. 深色正确：真浏览器 + CDP 的 `prefers-color-scheme`，实测正文 `--yuki-ink-2`、标题 `--yuki-foreground`、
   元信息 `--yuki-muted-foreground`、分隔线 `--yuki-border` 都换成深色那套值，页面底色 `--yuki-background`
   （对比度 10.62:1）。
5. 窄屏正确：375px 下每条都不溢出列表，且仍是紧凑的一小条。
6. 可点可评论：每条都有自己的 permalink（在标题里），评论链接指向 `#comments`，链接落到的文章页上
   `#commentform` 在；无标题那条也在这一条里验了。

**共享状态提醒**：造数会把「承载说说的分类」这个全站 theme mod 指向自己的分类，工单 04 的造数也写它——
两个会话的验收同时跑会互相盖。所以第一个断言先回读归档页标题，不是本脚本那个分类就直说是
「共享状态被别处改了」，而不是让后面的版式断言以莫名其妙的方式红。
