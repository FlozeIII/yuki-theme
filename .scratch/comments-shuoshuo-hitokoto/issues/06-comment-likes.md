# 06: 评论点赞

**What to build:** 访客能给一条评论点赞，看到每条评论的计数，也能看出自己点过哪些；再点一次取消。同一个访客对同一条评论只计一次。整个过程不刷新页面。

计数存在评论上。识别访客用站点 cookie——这挡得住手滑和刷新，挡不住刻意清 cookie，对个人博客的量级够用，因此不引入账号，也不把 IP 存库。

**Blocked by:** 03

**Status:** ready-for-agent

- [x] 点赞后计数加一，页面不刷新
- [x] 再点一次取消点赞，计数减一
- [x] 同一访客重复点赞不会让计数继续增加
- [x] 页面重新加载后，已点赞的状态仍然显示正确
- [x] 计数不因为刷新或重新访问而失真
- [x] 点赞控件使用主题的设计 token，深色模式与窄屏下表现正确
- [x] 浏览器禁用 JS 时，页面不因此报错或残缺

## Comments

实现：`b5ec512`。验证方式：`node tests/bin/verify-comment-likes.mjs` —— **63/63 通过**。

### 形状

代码在 `inc/comment-likes.php`（`functions.php` 里显式 require 接上——这是 2026-10-15 定下的
并行会话规矩第 2 条：功能代码优先放新文件，改共享文件的一行总比改它的一百行容易对账）。

- 「谁点过」是评论元数据里的一份**名单**（存访客标识的 HMAC），**计数就是名单长度**。
- 访客身份是站点自己发的 cookie（32 位随机十六进制，httpOnly、SameSite=Lax、5 年），
  存库的是它的 HMAC——那个字符串本身就是凭证，库被看到时不该连它一起交出去。
- 写走 REST：`POST /wp-json/yuki/v1/comment-like`，body `{"comment_id":12,"liked":true}`，
  回 `{"count":2,"liked":true}`。
- 每次操作的计数与「我点过没有」都由**服务端**渲染进页面（`template-parts/comment-like.php`），
  `assets/js/comment-likes.js` 只让它点得动。

### 五处取舍

1. **计数 = 名单长度，不另存一个数字。** spec 的「涉及的数据」把「点赞计数」与「每位访客的
   点赞标记归属」并列为两项，这里只存后者——两个字段总有一天会不一致，而不一致时页面上会
   出现「显示 3 个赞、可你自己已经在名单里」这种自相矛盾。**这是有意偏离 spec 那半句措辞。**
2. **公开端点，不校 nonce。** 与评论表单同一个理由（WordPress 自己的评论表单也不校，缓存站点上
   加 nonce 会让访客莫名失败）。代价说清楚：不带 cookie 的请求每次都拿到新身份，**能把计数刷上去**，
   不是「最多切换一个赞」——挡它靠审核与站点限流，spec 认的就是这个尺度。
3. **初始状态由服务端渲染。** 禁用 JS 时计数照样看得见，也不必为了显示一个数字再问一次服务器。
   代价：开着页面缓存的站点上，渲染出来的「我点过没有」会串给别的访客（计数是准的，只有那枚
   高亮会串）。主题的评论表单那套令牌出于同一个理由也不设上界。
4. **待审评论不给点赞入口**：模板不渲染，端点也拒（404）。它还没公开，攒赞没有意义。
   （story 16 说的「每条评论」指的是访客能看到的那一些。）
5. **JS 先乐观画、失败退回，数字以服务端回话为准**：回话之前点下去不该毫无反应，而
   重复点、另一个标签页点过、本地那点算术，都可能让乐观值不对。

### 代码审查改掉的五处（都不是功能问题，是**验得不够**或**说得不准**）

1. **「禁用 JS」原本是空验**：只靠「计数在 HTML 里」+「按名字挑规则扫样式表」两条代理，而后者
   抓不到 `display:none` 挂在**外层容器**上的情形（上面那条变异证实了）。现在拆成它真正可能坏的
   两半：内容用不带 cookie 的普通请求断言（那就是没脚本的浏览器看到的东西），可见性去真浏览器里
   读**算过之后**的 display/visibility/opacity 与外层盒子。**并且如实写明**：这套基建里没有真开
   一个关掉脚本的浏览器（`browser.mjs` 没暴露那条 CDP 命令），所以验的是两半，不是那个场景本身。
2. **两条断言恒真**：「用到的 token 都定义过」「颜色 token 在 .dark 都定义过」在一个 token 都
   不用时也成立。补了一条前置断言（这块样式确实用到了 token，7 个、其中颜色 6 个）。
3. **一条断言被合成过**：「待审评论上没有点赞控件」原本把「看得到待审评论」也 `&&` 进去，
   visibility 那边一坏就会以「没有控件」的名义红。拆成两条。
4. **命名混了两个前缀**：访客身份那几个函数原本叫 `yuki_like_*`（可它们做的不是「赞」，是
   「这位访客是谁」），同节其余又是 `yuki_comment_*`。改成 `yuki_visitor_*` 与
   `yuki_comment_like_*` 两族，按「作用在什么上」命名，并在节首写明为什么分两族。
5. **同一个数字两处格式化**（PHP 用 `number_format_i18n`、JS 用 `toLocaleString`），站点语言与
   浏览器语言不一致时同一个数会长得不一样。改成两边都原样输出数字。
   另删掉一处冗余：`rest_sanitize_boolean()`（参数已声明 `type=boolean`，且
   `yuki_comment_set_like()` 自己会落成布尔）。

### 记录一处**超出勾选项**的东西

**端点边界那几条**（不存在的评论 404、`liked` 不是布尔 400、缺参数 400、待审评论 404）不在七条
勾选项里。留着是因为它们是这个端点**自己声明的契约**（REST 的 `args`），而其中两条 400 正是
「别人乱填时不会静默改计数」的证据；两条 404 是「不公开的东西点不了」的证据。

### 已知边界

- **并发下会丢一次赞**（读-改-写名单，两个人同一瞬间点同一条可能只记上一人）。代码注释里写了：
  这是个人博客的点赞数，不是账。
- **名单没有上限**：一条评论被人点了很多次，那份元数据就长那么大。真到了要担心的时候，该换的是
  存储方式，而不是加一个上限让计数变得可疑。
- **清掉 cookie 就能再点一次**——spec 明说这挡不住，也是它接受这个尺度的原因。
- **测试脚手架有重复**：`tryFx` / `waitFor` 与 `verify-shuoshuo.mjs` 那几份逐字重复。仓库的
  约定是公共辅助收进 `tests/bin/lib.mjs`（`theme-css.mjs` 就是为这个抽出来的），但 `lib.mjs`
  是共享文件、这一轮有三个会话在动它，挪过去要同时改别人的脚本，不在这单里做。
