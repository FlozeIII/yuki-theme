# 01: 本地测试基建（邮件捕获 + 上游 stub）

**What to build:** 本地验证环境具备两个观察点：所有发出的邮件被记录到文件，供测试取出正文；一言的上游可以被指向一个本地 stub，并能数出被命中的次数，也能被切换成故障状态。这是纯粹的测试基建，不改变主题对外的任何接口或行为。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] 提交一条评论后，邮件捕获文件里出现那封通知邮件，正文可读、其中的链接完整未被截断
- [x] 邮件捕获是本地环境的设施，不是主题的一部分——主题未启用时它同样工作
- [x] 上游 stub 能返回一个可控的响应体
- [x] 上游 stub 能被切换成 500，也能被整个停掉
- [x] 能读出 stub 被请求的次数
- [x] 主题代码里没有为测试而存在的分支、开关或钩子

## Comments

验证方式：`node tests/bin/verify-harness.mjs` —— **29/29 通过**（基建落在提交 `1147747`）。

**断言做过变异验证**，不是只看它绿：把捕获改成按 78 列折行 → 「长链接在正文里原样完整」变红；
把整个邮件捕获 mu-plugin 拿掉 → 三条与邮件相关的断言全部变红（含「主题未启用时照样工作」）。
变异测试还揪出我一条**永远不会失败**的断言（「邮件里没有链接被折断」——折行劈开的片段各自
都不含空白，于是恒真），已删掉并在原处写明原因。绿过一次不等于验到了东西。

装法：`node tests/bin/harness.mjs install`，把 `tests/wp/mu-plugins/yuki-dev-*.php` 复制进
`wp-content/mu-plugins/`，并在 WordPress 目录的同级建 `var/`（捕获文件与 stub 状态都在仓库之外）。
接口与注意事项见 `tests/README.md`。

六条各自落在哪里：

1. 走**真实评论表单**提交，捕获文件里出现审核通知：正文 978 字符，植入的 **196 字符长链接原样完整**
   ——它超过 PHPMailer 的 78 折行宽度，所以这条断言真能验出截断（变异验证：改成折行即变红）。
   另确认 `WordWrap` 默认为 `0`，真实发送也不折行。
2. 在**独立进程**里把启用主题切成 `twentytwentyfive`，再用 HTTP 发新请求提交 —— 邮件照样被捕获。
   必须在另一个进程里做：`switch_theme()` 只换选项，不卸掉已加载的旧主题代码，同进程里验的不是「未启用」。
3. `var/upstream/body.txt` 决定返回正文。
4. `var/upstream/mode` 写 `500`（或 `garbage`）；**整个停掉 = 杀掉 stub 进程**，端口不再监听、连接被拒。
5. `var/upstream/hits.log` 的行数，或 `GET /__hits`。
6. 扫主题源码，无 `YUKI_DEV` / `pre_wp_mail` / `pre_http_request` / `127.0.0.1` 之类的痕迹。

**刻意改动产品行为的地方只有一处**：内核的评论频率限制（15 秒硬编码、无筛子可调，
`comment.php:2315`）在本地环境里被关掉。理由是它按 IP+邮箱去重，而本地每个请求都是 `127.0.0.1`，
区分不了测试套件和攻击者；更要紧的是它会让工单 02 的「渲染到提交不足 3 秒」断言**假通过**——
那种提交必然落在那 15 秒窗口里。理由与影响写在 `tests/wp/mu-plugins/yuki-dev-comment-flood.php` 的文件头。

**本地环境是共享的**：同一台机器上可能同时开着别的会话，共写同一份 WordPress 与同一份 `var/`。
因此基建不提供清空捕获文件的操作，改用 `markMails()` 字节偏移 + `readMails(偏移)`；
验收只认带本次标记的那封邮件，而不是「文件里多了几封」。并发下的注意事项见 `tests/README.md`。
