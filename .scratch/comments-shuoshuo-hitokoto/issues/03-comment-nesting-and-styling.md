# 03: 评论区的层级与样式

**What to build:** 评论区看起来是主题的一部分，而不是一块外来的东西。回复最多嵌套两层，更深的回复被压平到第二层而不是继续缩进；评论列表、表单、输入框、按钮全部改用主题的设计 token，深色模式下配色正确。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] 三层以上的回复链，最深的回复渲染在第二层的位置，缩进不再继续增加
- [x] 每一层仍能看出谁在回复谁，不靠缩进也知道层级
- [x] 评论列表、表单、按钮使用主题的 CSS 变量，评论区里不出现硬编码色值
- [x] 深色模式下评论区配色正确、正文对比度可读
- [x] 窄屏下评论不因为缩进而被挤成一条缝
- [x] 评论的既有行为不变（列表、回复、表单提交的结果与改动前一致）

## Comments

实现：`e127eb2`（样式、评论印记、验收脚本）+ `cbb0c9f`（压平、回复指示器、接线）。
验证方式：`node tests/bin/verify-comment-nesting.mjs` —— **50/50 通过**。

**压平不是把深的藏起来。**（这一段最初写错了，代码审查指出后实测更正。）核心自己就有「到顶平铺」：
`Walker_Comment::display_element()` 在到达 `max_depth` 时会把那个元素的子回复就地铺在当前层，
不让它们被甩到列表末尾——所以把 `max_depth` 设成 2 **也能**得到「一层 children、全部 depth-2」，
那些回复不会消失。但它同时把这个 2 交给了 `comment_reply_link()`，第二层的评论因此没有回复入口，
讨论到第二层就断了。

所以这里换了另一种做法：不动 `max_depth`（站点设置的五层照旧），只改**显示用的那棵树的父指针**——
深于两层的评论改挂到它的顶层祖先下。这样第二层仍能回复，新回复同样铺在第二层，顺序也按时间排。
**数据库里的父子关系一个字节都不动**——换主题、换插件，评论树还是原样。改的是 `clone`：
`WP_Comment` 是全局评论缓存里的实例，就地改 `comment_parent` 会连累同一次请求里别的消费者
（小工具、feed）。父评论不在本页时（父评论被删、或列表被别的东西截断）不动它，交给核心照原样处理。

**「谁在回复谁」靠标签，不靠缩进。** 压平之后缩进不再说明得了层级，所以每条回复都标一句
「回复 @谁」，用的是它**真正**回的那条（压平时把真父评论记在 `yuki_comment_reply_target()` 里）。
第二层在缩进之外还加了一道主色竖线，窄屏缩进收窄之后仍认得出层级。

**每条评论由主题自己渲染**（`comments.php` 传 `callback`，印记在 `template-parts/comment.php`）。
必须这样做的原因只有一个：核心的印记里没有安放「回复 @谁」的位置。代价是这份印记要跟着核心走，
所以文件头写明了四处不能改的东西（两个 id、`comment_class()`、末尾不自己关 `</li>`），以及走
callback 时核心不会挂的两个行为，这里都补上了：待审评论对非作者过滤正文 HTML（且要在其它
`comment_text` 过滤器跑完之后再剥，否则连段落都保不住）、短 ping 的简印记。

六条各自落在哪里：

1. 造数造一条四层深的链子（讨论设置里的嵌套层数**刻意设成 5**，验的是主题自己压平），
   断言第二层的三条都在 `depth-2`、最深不超过 2、整页只有一个 `children` 容器、顺序没被打乱。
2. 二层标「回复 @顶层甲」，被压平的三层标「回复 @二层乙」、四层标「回复 @三层丙」，顶层不标。
3. 静态读 `style.css`：评论区规则里没有 hex/rgb/hsl/命名色；用到的每个颜色 token 在 `:root`
   与 `.dark` 里都有定义（漏掉哪个，深色下就会是浅色那套值）。
4. 静态核对之外，用无头 Edge + CDP 真量了一遍（`tests/bin/browser.mjs`，Node 自带 WebSocket）：
   深浅两色走的是 CDP 的 `prefers-color-scheme`，也就是**主题自己的那条分支**，不是给页面塞个 class
   假装。实测评论卡片底色就是对应 token（浅 `#FFFFFF` / 深 `#22222B`）、正文颜色就是 `--yuki-ink-2`，
   按实测颜色算的对比度 6.55:1 / 9.48:1。
5. 静态核对（二层缩进 28px、窄屏媒体查询收到 12px）之外，同样在真浏览器里量：375px 视口下
   第一层卡片 312px、第二层 300px——只差一个缩进，不是被挤成一条缝，也没多出第二层缩进。
6. 走**真实评论表单**回一条给二层评论：提交被接受、渲染在 `depth-2`、标出「回复 @二层乙」、
   没有多出第二层 children；另外核了 comment-reply.js 要的五个元素都在（评论 id、评论体 id、
   父评论字段、表单 id、回复区 id），以及 pingback 这类非 comment 类型照旧渲染、页面没有 PHP 报错。
   工单 02 的 34 条（表单提交、待审、防垃圾）与工单 01 的验收也一并重跑过，全绿。
   另外补了**待审那一条**的四条（管理员看自己那条未过审的评论）：可见、有「正在等待审核」提示、
   正文里的标签被剥掉但文字还在、不给回复链接——这四条覆盖的正是核心在 `start_el` 里挂的
   `filter_comment_text` 那套行为，走 callback 时不会自动挂上，只能自己补。

**已知的一点取舍**：开着分页（`page_comments`）的站上，压平会让「每页几条」与页码统计略有出入
（页数是核心在过滤之前算的）。本地与默认配置都不开分页；真要开，观感是某页稍多或稍少几条评论。 

**一条不属于本工单的发现，已单独查清并修复**：窄屏下页脚「订阅」那一行横向溢出。

当时记的是「375px」，真浏览器逐档量过（320 / 360 / 375 / 390 / 414 / 480 / 640 / 768 / 1024 / 1200）
之后，宽度**记高了一档**：320px 下整页溢出 **20px**，360px 下那一行内部挤 4px，
**375px 及以上是干净的**。所以首页那些页面本身没问题，问题在页脚那一行。

撑出去的是 `.yuki-newsletter form` 这个 flex 行：输入框写着 `flex: 1`，但 flex 项的 `min-width`
默认是 `auto`，输入框的**固有宽度（227px）就成了地板**，它不肯再缩——整行要 325px 而视口只有 305px，
按钮因此被从 76px 挤到 62px（「被切」的观感来自这里，不是 hero 标语）。

**是主题本来就这样**：规则来自初始提交 `8e5832f`，`footer.php` 本轮没人动过，也与评论改造无关。
`style.css` 里此前**没有**任何针对它的媒体查询。

修法：给那个输入框加 `min-width: 0`（搜索框那条 `.yuki-search-form label` 本来就是这么写的）。
A/B 实测：加之前 320px 溢出 20px，加之后 0px，还原回去又是 20px——差别确实来自这一处。
