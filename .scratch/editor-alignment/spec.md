# 前台呈现与编辑器对齐

Status: ready-for-agent
Type: spec

## Problem Statement

主题能读、能发、评论也能就地落位了，但**正文长什么样，取决于内容从哪条路进来**：

- **对齐与图注没有样式。** `.alignleft`、`.alignright`、`.aligncenter`、`.wp-caption`、
  `.wp-caption-text`、`.gallery-caption` 一个都不存在。从别处粘进来的一张对齐图、一段图注、一个画廊，
  在主题里长成没排过的样子。
- **宽对齐完全不存在。** 没有 `align-wide` 声明，也没有 `.alignwide`/`.alignfull` 的宽度规则。
  区块编辑器里选了「宽」或「全宽」，前台没有任何变化。
- **编辑器里看到的不是主题。** 正文样式全挂在 `.yuki-prose` 下，而编辑器画布是
  `.editor-styles-wrapper`。作者在编辑器里写字的字体、字号、行高、引用、代码块、图片圆角，
  与前台上看到的不一样——**写完再切到前台看**，是这个主题今天唯一的工作方式。
- **宽度是硬编码的。** 容器 1120px 与窄栏 768px 直接写在规则里，`DESIGN.md` 没有布局一节，
  「正文列宽」没有一个可以被引用的名字。

Theme Check 把这些报成 RECOMMENDED。它们不是规范仪式：前两条是使用者会撞上的**呈现缺陷**，
第三条是作者每天都会遇到的**编辑体验缺陷**。

## Solution

把「正文在多宽的地方、以什么样子呈现」变成一份**两边共享的契约**：

**一份宽度定义。** 把正文列宽、宽对齐宽度、容器、侧栏与间距收成 CSS 变量，`DESIGN.md` 增加布局一节。
单篇有侧栏，宽对齐在主列里退化为正文列宽；没有侧栏的模板才真正放宽。这个差异是刻意的。

**一组正文呈现类。** 对齐、图注、画廊图注按主题的 token 写样式；置顶文章与作者本人的评论各有一个
克制的标记。**不新添颜色**——需要新色是 `DESIGN.md` 的事。

**一次编辑器接入。** `add_editor_style()` 直接把 `style.css` 交给编辑器，正文规则的选择器同时覆盖
`.yuki-prose` 与 `.editor-styles-wrapper`。不另立编辑器样式表，不引入构建步骤。

**保持 classic 形态。** 不引入 `theme.json`（ADR 0003），CSS 仍是视觉规范的唯一来源。

## User Stories

### 对齐与图注

1. 作为作者，我希望在正文里放的左对齐/右对齐图片真的浮在文字旁边，这样图文混排成立。
2. 作为作者，我希望居中的图片与文字块真的居中，这样从别处粘来的内容不会被拉成默认的左对齐。
3. 作为作者，我希望图片带图注时，图注是主题的样子（字号、颜色、间距），而不是浏览器默认。
4. 作为作者，我希望画廊的图注也长成主题的样子，这样画廊与单张图片不像是两个主题做的。
5. 作为访客，我希望对齐后的图片不会挤进侧栏、也不会让正文出现横向滚动。
6. 作为作者，我希望置顶文章在列表里有一个克制的标记，这样我能一眼看出它被置顶了。
7. 作为访客，我希望作者本人的评论在评论区里有一个克制的标记，而不是与普通访客完全一样。
8. 作为设计者，我希望这些标记只用现有 token，不为了「有标记」新添一枚颜色。

### 宽对齐

9. 作为作者，我希望在页面与说说里可以把图片/封面设为「宽」，它会比正文更宽，这样长图有呼吸的空间。
10. 作为作者，我希望在单篇文章里设「宽」不会把内容压到侧栏上——单篇的主列就是正文列，宽对齐在那里
    退化为正文列宽。
11. 作为访客，我希望宽块在任何断点下都不溢出视口，也不遮住侧栏。
12. 作为作者，我希望嵌入（视频、推文等）自动适应正文宽度，而不是撑破布局。

### 编辑器

13. 作为作者，我希望在编辑器里看到与前台一致的字体栈、字号、行高与正文颜色，这样我不用发布后再切到前台看。
14. 作为作者，我希望引用、代码块、图片圆角、图注在编辑器里就是主题的样子。
15. 作为作者，我希望编辑器的正文画布与单篇文章的正文文字宽一样（约 720px），这样换行位置与前台接近。
16. 作为作者，我希望知道「页面里的宽块在编辑器里按正文列预览」——这是已知的差异，不是漏做。
17. 作为设计者，我希望编辑器与前台共用同一份 `style.css`，而不是一份会漂移的副本。
18. 作为设计者，我希望深色 token 不进入编辑器——深色是访客浏览器里的开关，编辑器读不到它。

### 边界

19. 作为设计者，我希望这一轮**不引入 `theme.json`**（ADR 0003）。
20. 作为设计者，我希望这一轮**不注册区块样式与区块样板**——那是使用者的版式库，不是主题的呈现契约。
21. 作为设计者，我希望这一轮**不加载 `wp-block-styles`**，避免核心默认区块样式与手写的正文样式互相覆盖。
22. 作为设计者，我希望宽度只有一个定义处，改 `DESIGN.md` 与 CSS 变量就能改布局，而不是满文件找数字。

## Implementation Decisions

### 通用约束

- 目标形态仍是 classic 主题（ADR 0003）：不引入 `theme.json`、不引入构建步骤。
- 视觉 token 只来自 `style.css` 的 `:root` 与 `.dark`，数值规范来自 `DESIGN.md`。
- 不新添颜色。需要新色时先改 `DESIGN.md`，再改 token。
- 这一件只做呈现：不改评论提交、不改说说数据、不改一言。

### 宽度契约

把布局宽度收成 CSS 变量，并让现有规则引用它们。建议的名称与数值：

```css
--yuki-content-width: 768px;   /* 窄栏容器外宽（含 24px 内边距；文字宽约 720） */
--yuki-wide-width: 1120px;     /* 宽对齐能达到的最大宽度 */
--yuki-container-width: 1120px;/* 页面容器外宽（含 24px 内边距） */
--yuki-sidebar-width: 300px;
--yuki-layout-gap: 48px;
```

- `.yuki-container`、`.yuki-narrow`、`.yuki-post-list`、`.yuki-article-header`、`.yuki-single-layout`
  改为引用变量，不再各写一个数字。
- **单篇的宽对齐退化为正文列宽。** 容器内容宽 1072，单篇主列 = 1072 − 300 − 48 = **724px**；
  正文文字宽约 720px，没有「比正文更宽」的空间。宽块在单篇里只做约束，不越界、不遮侧栏。
- **无侧栏模板（`page.php`、说说）的宽对齐可到 1120px**，用负外边距或等价的宽度规则突破窄栏。
- `DESIGN.md` 增加「布局」一节，记录上面这几个数值与单篇/无侧栏的差异。**不要把这个差异当 bug 修掉。**
- 在 `after_setup_theme` 里加 `add_theme_support( 'align-wide' )` 与
  `add_theme_support( 'responsive-embeds' )`。**不加 `wp-block-styles`**：核心那套默认区块样式会与
  手写的 `.yuki-prose` 规则争同一批元素。
- 不设置 `$GLOBALS['content_width']`——本主题的宽度由 CSS 变量表达，核心那个全局变量在这里只会成为
  第二个来源。

### 正文呈现类

全部写在 `.yuki-prose`（以及编辑器的别名作用域）下，只用现有 token：

| 类 | 呈现 |
| --- | --- |
| `.alignleft` | 左浮动，右侧留出文字间距 |
| `.alignright` | 右浮动，左侧留出文字间距 |
| `.aligncenter` | 块级居中 |
| `.wp-caption` | 图注容器：最大宽度 100%，图片与图注成组 |
| `.wp-caption-text` | 图注字号/颜色/间距，沿用 `--yuki-ink-2` 一类的弱化色 |
| `.gallery-caption` | 画廊图注，与 `.wp-caption-text` 同一套规则 |
| `.sticky` | 置顶文章：列表项左侧一条主色竖线，或一枚小徽章；不改变布局 |
| `.bypostauthor` | 作者本人的评论：中性色描边或小标签；不引入新颜色 |

- 浮动类必须有清除机制，避免后续内容绕排到图片旁边。
- 窄屏（与现有断点一致）下左/右浮动收成居中或占满宽度，防止横向溢出。
- `.sticky` 与 `.bypostauthor` 是**语义标记**，不是装饰；样式要克制到不影响阅读节奏。

### 编辑器接入

- 加 `add_theme_support( 'editor-styles' )` 与 `add_editor_style( 'style.css' )`。
- 正文规则的选择器改成 `:is(.yuki-prose, .editor-styles-wrapper)`（或其等价写法），
  让同一组规则同时命中前台正文与编辑器画布。**不新建 `assets/css/editor.css`。**
- 编辑器画布宽度约束为正文文字宽（约 720px），并居中。`page.php` 里会放宽到 1120px 的宽块，
  在编辑器里按 720px 预览——这是已知差异，写进工单，不要为它再叠一层编辑器专用布局。
- 编辑器只使用浅色 token。`.dark` 下的规则不进入编辑器；不为编辑器另做深色。
- `style.css` 里的头部/侧栏/页脚规则会被一并载入编辑器。它们在没有对应标记时不会命中，
  属于可接受的成本；若实测出现可见污染，再在工单里记录并收紧选择器，**不要**因此拆文件。

### 明确不做的

- 不引入 `theme.json`（ADR 0003）。
- 不注册区块样式（`register_block_style`）与区块样板（`register_block_pattern`）。
- 不加载 `wp-block-styles`。
- 不为编辑器做深色形态。
- 不把单篇改成单栏，也不让宽块跨过侧栏。
- 不动 `custom-header` / `custom-background`、`Theme URI` / `Author URI`、版权声明——
  它们继续作为已知残留记录在发布工单里。

## Testing Decisions

### 什么算一个好测试

只断言**外部可观察的产物**：CSS 里有哪条规则、页面加载了哪份样式表、编辑器画布里算出来的宽度与字体。
不断言「调用了哪个 PHP 函数」这种实现细节。

### Seam

沿用现有观察点，不新建产品接口：

1. **文件阅读**——`tests/bin/theme-css.mjs` 已把 `style.css` 读成文本并统一行尾；静态断言直接用它。
2. **HTTP**——前台页面里正文容器的实际宽度、对齐图片的 `float`/`text-align`、宽块的宽度。
3. **无头浏览器**——登录后的编辑器页面，断言编辑器画布确实加载了主题样式表，并量出画布宽度与字体。
   这是这一件唯一新增的「眼睛」，因为它要证的事（样式声明了但编辑器没加载）静态断言证不了。
4. **PHP 探针**——`wp-probe.php` / WP-CLI 断言 `get_editor_stylesheets()` 含 `style.css`。

### 要测的模块

- **8 个类都存在**，且对齐类在前台生效（浏览器里读到 `float` / `text-align`，不是只在 CSS 里有字符串）。
- **宽度变量存在并被引用**：变量定义在 `:root`；容器/窄栏规则里不再有裸的 1120/768。
- **宽对齐的边界**：单篇里宽块不越过主列、不遮侧栏；无侧栏模板里确实更宽；所有断点无横向滚动。
- **编辑器确实套上了样式**：编辑器页面加载 `style.css`；画布宽度约 720px；字体栈与正文颜色与前台一致。
- **编辑器验收的退路**：登录自动化不成立时，退到「PHP 探针 + 人工截图」，并在工单里写明用了哪条路。
- **没有新颜色**：新增规则里的色值全部来自已定义的 token（沿用 `verify-comment-likes.mjs` 的检查方式）。

### 明确不测什么

- Theme Check 的结论——发布前跑一次，不进验收脚本。
- 区块编辑器界面本身（工具栏、侧栏面板）。
- WordPress 的区块渲染逻辑——那是平台的事。

## Out of Scope

- `theme.json` 与区块主题形态（ADR 0003）。
- `register_block_style`、`register_block_pattern`、`wp-block-styles`。
- 编辑器深色形态。
- 单篇改单栏、宽块跨侧栏。
- `custom-header` / `custom-background`、`Theme URI` / `Author URI`、版权声明。
- 评论提交、说说数据与一言的行为。
- `comment-reply`：已在 `inc/comment-submit.php:408` 作为依赖排上；Theme Check 的 INFO 是误报，
  记在发布工单里，不在这一件处理。

## Further Notes

- `functions.php` 与 `style.css` 在 `AGENTS.md` 的共享文件清单上。开工前在 `.scratch/holds.md` 挂一行，
  提交后删掉；提交只带自己的路径。
- `DESIGN.md` 不在共享清单上，但它是视觉规范；布局一节要与 CSS 变量同一提交落地，避免文档与代码漂移。
- 这一件做完后，Theme Check 的预期变化：`add_editor_style`、`responsive-embeds`、`align-wide`
  与 8 个 CSS 类共 **11 条 RECOMMENDED 消失**；`register_block_pattern`、`register_block_style`、
  `wp-block-styles` 仍留（刻意的）。REQUIRED 仍只有 `readme.txt` 一条（ADR 0002 主动接受）。
- 编辑器画布的约 720px 与单篇正文文字宽一致；页面模板里 1120px 的宽块预览不出来。这条差异要在
  `docs/RELEASING.md` 或工单里留一句，防止下一个人把它当缺陷。
- 评论线的 `comment-submit.js` 会读 `#respond` 的位置；本件不动评论区，避免与那条线互相踩。
